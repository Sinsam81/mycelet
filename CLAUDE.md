# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mycelet (rebranded from SoppJakt 2026-05-09) — a Norwegian (and Swedish) mushroom-foraging app. UI strings, docs, and commit messages are in Norwegian. Code identifiers and CLAUDE-facing notes are in English.

Stack: Next.js 16 (App Router, Turbopack) + React 19 + TypeScript + Tailwind + Supabase (PostGIS) + Stripe + Leaflet 5. State via Zustand and TanStack Query. Tests via Vitest.

## Common commands

```
npm run dev         # Next dev server on http://localhost:3000
npm run build       # production build (Turbopack; runs tsc as part of build)
npm run typecheck   # tsc --noEmit
npm run lint        # next lint
npm run test        # vitest (runs all tests)
npm run test -- src/lib/weather    # filter by path

npm run qa          # full product evaluation (Playwright) vs local dev — the main QA loop
npm run qa:prod     # read-only smoke + gating vs live mycelet.com (safe against prod)
npm run qa:setup    # create the dedicated QA test user (run once)
npm run qa:report   # open the last Playwright HTML report
```

Tests use the `@/*` path alias from `tsconfig.json`; vitest mirrors this in `vitest.config.ts`. Add new tests next to source in `__tests__/` folders — they pick the alias up automatically.

There is no Supabase CLI workflow set up; migrations are applied by pasting `supabase/migrations/NNN_*.sql` into the Supabase SQL Editor in number order (001 → 076 at the time of writing; the ledger lists 074, 075 and 076 as not yet run — 074 is pasted the same day as the release it shipped with, *after* the deploy, 075 is urgent and independent of any release, and 076 is independent and can go in any time; see the sections at the top of the ledger). Which of them are actually applied in production is tracked per migration in `docs/migrasjoner-a-kjore.md` — **the statuses there for 039 onward are unconfirmed until the owner has checked them against the database; do not assume a migration is applied (or not) from this file.** A PR that adds a migration adds its row to that ledger — to the table and to the single read-only query there that answers for every migration from 039 (`src/lib/__tests__/migrasjonshovedbok.test.ts` fails if either is missing). Only paste a file whose row reads `false`: the ledger lists where an early migration pasted after a later one bites (041 after 056, 042 after 075, 043 after 054, 049 after 065, 066/067 after 068). **041 is not pasted at all any more:** 076 does its parts 2 and 3 (the comment counter and the recount), and the ledger's row for 041 reads `true` once 076 has run; its part 1 conflicts with 056, so the profile post count that leaves out hidden posts still needs a new migration after 056. They have hard dependencies — running 003 alone fails because it references `mushroom_species` and `update_updated_at()` from 001. Migration 008 (audit log) requires `moderator_roles` from 002.

## QA automation & standing habits

**Full product evaluation loop** — Mycelet's main QA automation. `npm run qa` drives every core flow (map + NO/SE geo-routing, AI identify, prediction, calendar, forum, auth + forgot-password, billing web/native gating, species, /datakilder, /api/health) against the success criteria in `docs/qa-sjekkliste.md` and reports breakage. It **detects + reports + proposes fixes for approval — it must NEVER auto-deploy to the live app.** Run it via the `/loop` skill (the exact prompt is in `docs/qa-sjekkliste.md`).
- Engine: Playwright, `e2e/*.e2e.ts`, three projects (`setup` → login, `public` → no-auth, `authed` → uses the saved session). Config: `playwright.config.ts`.
- `npm run qa` targets local dev (auto-starts/reuses the dev server); `npm run qa:prod` runs the read-only subset against live mycelet.com. It runs *your checkout's* cases, so a case written for code that is not deployed yet fails there until the deploy — the `qa:prod` run that means something is the one after it.
- Needs a dedicated QA user (`npm run qa:setup`, idempotent; writes `QA_TEST_EMAIL`/`QA_TEST_PASSWORD` to `.env.local`). Authed tests skip cleanly if it's missing.
- Keep authed tests **read-only** — there's one Supabase project (no staging), so writes hit prod. Write flows (post forum, save finding, real AI upload) stay manual (🖐️ in the checklist). Usage measurement (`<RegistrerBruksdag>` → `bruksdager`) skips `navigator.webdriver` browsers for the same reason — don't remove that guard.
- **Gotcha:** `/soppforhold` server-renders by fetching its own `/api/prediction/regions`, so `SOPPFORHOLD_BASE` must point at localhost in dev. It used to be hardcoded to production, which meant the page showed prod data no matter what you changed locally — a verdict change gave a fresh API response and a stale page on the same machine, and the fix looked like it hadn't worked. Preview deploys still read production on purpose (a build fetching its own not-yet-deployed URL is chicken-and-egg).
- **Gotcha:** Next/Turbopack does NOT run middleware in local dev, so middleware-only auth gating (`/profile`, `/admin`, `/forum/new`) can't be tested locally — those assertions skip on `npm run qa` and run on `npm run qa:prod` (prod has real middleware). Page-level `redirect()` gating (`/mine-steder`, `/map`, `/identifiseringer`, `/forum/moderation`) works in both — **but assert on the final URL in a browser, never on the HTTP status.** `/map`, `/mine-steder`, `/profile` and `/identifiseringer` have a `loading.tsx` since Nov 2026, so the response is already streaming the skeleton when the page calls `redirect()`: locally that arrives as a **200 plus a client-side redirect**, not a 307. `page.goto` + `toHaveURL(/auth\/login/)` (what `e2e/auth-pages.e2e.ts` does) still passes; `request.get()` or `curl -I` sees 200 and looks like broken gating. In production the middleware redirects before the page starts, so the status is real there. See «`loading.tsx` makes the route stream» under Framework quirks.

**Recent-feedback sweep (do this every time the owner reports a bug):** (1) fix the reported bug; (2) audit the WHOLE app for siblings of that bug-class (same wrong assumption/pattern elsewhere); (3) fix the siblings + verify with `npm run build` (delete iCloud `* 2.ts` dupes first — see below); (4) deploy only when the owner says OK. Proven value: the Swedish-blank-map bug's sibling was the Göteborg region-routing bug — both Norway-centric assumptions.

## Architecture

**App Router layout.** UI lives under `src/app/`. API routes are colocated under `src/app/api/<name>/route.ts`. Pages and routes share the same Next.js conventions; treat `route.ts` as the API contract.

**Supabase client split** (`src/lib/supabase/`):
- `client.ts` — browser client (anon key). Used in `'use client'` components and hooks.
- `server.ts` — server client with cookie-based session. Used in server components and route handlers. Note: `cookies()` is async in Next 15+; the server client awaits the promise inside its callbacks so call sites can stay synchronous.
- `middleware.ts` — session refresh + route gating + per-request correlation ID. The root `middleware.ts` re-exports it.
- `admin.ts` — service-role client. Server-only, never import from client code. Requires `SUPABASE_SERVICE_ROLE_KEY` in env.

**Auth gating** lives in `src/lib/supabase/middleware.ts`. The `PROTECTED_PATHS` array there is the source of truth for which routes redirect unauthenticated users to `/auth/login?redirect=…`. Add new protected routes by editing that list.

**Password reset is our own mail, not Supabase's.** `/auth/forgot` posts to `POST /api/auth/glemt-passord`, which calls `auth.admin.generateLink({type:'recovery'})` and mails `https://www.mycelet.com/auth/reset?token_hash=…` through Resend (nb/sv, `src/lib/auth/glemt-passord-epost.ts`). `/auth/reset` redeems it with `verifyOtp` **on submit, not on load** (mail scanners must not burn the one-time token) and works in any browser. Supabase's own recovery mail is a PKCE `?code=` that only works in the browser that requested it — from the iOS shell the link always opens in Safari, so app users could never reset. The route always answers 200 and treats an unknown address, a bad body and a hit rate limit alike (no account enumeration), rate-limits per client and per address (generateLink bypasses Supabase's own mail throttle) and never logs the token or address. **It has two different fallbacks, because `generateLink` stamps `recovery_sent_at` and Supabase's own `/recover` then answers 429 for 60 s:** `fallback: true` means no link was made (service-role key or Resend not configured, or `generateLink` failed) — the form calls `resetPasswordForEmail` at once, and the `?code=` path on `/auth/reset` is kept for that. `sendFailed: true` means the link was made but the mail did not go out (one retry after 1 s with the same Resend idempotency key) — the form must not chain `resetPasswordForEmail` (it would get the 429, and every new call to the route re-stamps), so it says «vent et minutt og prøv igjen» and sends the next attempt straight to Supabase without calling the route. Answering `fallback` for both would take password reset down for everyone for as long as Resend fails. The route's own `maxDuration` (40) covers the worst case — `generateLink`, a send under `RESEND_FRIST_MS`, the 1 s pause and a second send, about 32 s: on the platform default it could be cut off mid-retry, after the link had already blocked Supabase's own mail for 60 s. On `/auth/reset`, only a 4xx answer other than 429 from `verifyOtp` means the link is dead: auth-js also returns network failures, 429 and 5xx in `error` (`erForbigaaendeAuthFeil` in `src/lib/auth/auth-feil.ts`), and those keep the token and the form. The consumed token is dropped from sessionStorage as soon as `verifyOtp` succeeds, so a reload finds the recovery session instead of retrying a used token. Do not add `recovery` to `/auth/confirm`; that route discards the session on purpose. App-created accounts (`user_metadata.plattform`) that finish the reset in Safari are signed out there and told to open the app.

**«Send bekreftelsen på nytt» depends on a dashboard template.** The button on `/auth/login` calls `supabase.auth.resend({type:'signup'})`, and auth-js sends no `code_challenge` there, so the resent link is not a PKCE link like the first one from `signUp`. That is fine only while the Supabase «Confirm signup» template points at `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup` (`src/app/auth/confirm/route.ts` redeems both kinds in any browser). With `{{ .ConfirmationURL }}` the resent link would be implicit-flow and leave the session in the URL fragment of a page that never reads it — then move the resend server-side (`generateLink` + our own mail to `/auth/confirm`, as the purre cron does). A confirmation link that still goes through `/auth/callback` and is expired, used or superseded arrives there without `code` and with `error_code=otp_expired`; the callback sends exactly that case to `/auth/login?linkExpired=1` (a cancelled Google sign-in also arrives without `code` and must not get that notice).

**Auth errors are mapped, never shown raw** (`authFeilNokkel` in `src/lib/auth/auth-feil.ts` → the `AuthErrors` namespace). Login, forgot and reset printed `err.message`; an AuthError *is* an Error, so the translated fallbacks never fired, and Norwegian and Swedish users got «Invalid login credentials» on the one screen every returning user meets. An unknown error maps to `null`, the page shows its own general text, and `varsleUkjentAuthFeil` logs code, name and status only — the message can contain the address. The same file's `erForbigaaendeAuthFeil` is the rule for «did the server actually refuse, or did no usable answer come?»: auth-js puts network failures, 429 and 5xx in `error`, and code that reads any `error` as a verdict throws away a valid reset token — or, in the Stripe webhook, would have cancelled a paying customer (see «Calls out of the billing handlers»).

**The date line on the plan card** (`periodelinje` in `src/lib/billing/kanal.ts`, shown on `/pricing` and `/profile`) says what the date means for the channel the plan was bought in. Two App Store rules: a trial shows the cancel deadline — trial end minus 24 h, the same `avslutningsfrist()` the reminder mail uses — for as long as that deadline is ahead, and «Første belastning senest {date}» after it (which is also what a three-minute sandbox trial gets), never Stripe's «Første belastning {trial end}», because Apple attempts the charge during the last 24 h; and «Sagt opp – … du belastes ikke igjen» is promised only when the row's last RevenueCat event (`metadata.rc_event_type`) was `CANCELLATION`, because `BILLING_ISSUE` with a grace period writes the same `active` + `cancel_at_period_end` while Apple keeps retrying the charge. That reading is only safe because the webhook never *writes* the CANCELLATION RevenueCat sends alongside a billing problem (next paragraph) — the «Kjent grense» comment in `kanal.ts` says so, and if that CANCELLATION is ever written again the hole is back. Dates are formatted in Europe/Oslo by `periodelinjeVerdier` — `/profile` renders on a UTC server. The same Apple rule holds **before** the purchase: in the iOS shell (`isNativePlatform` in the trial sheet, `useIsNative` on `/pricing`) the deadline is 24 hours before the trial ends, never the trial-end date — the trial terms (`ProvGratisArk.passVilkaarProveApp` / `passVilkaarProveUkjentLengdeApp`) say «senest 24 timer før prøveperioden er over», the plan card's renewal line «avslutt senest 24 timer før den slutter» (`Pricing.renewsOnEtterProveApp`) or, with the trial length unknown, «Avslutt senest 24 timer før prøven slutter» (`renewsOnProveUkjentLengdeApp`). With the web wording in the app, someone who cancelled the evening before trial end could already have been charged the year. No clock time before purchase: RevenueCat reports a one-month intro offer as 30 days, so a computed time could fall after Apple's. The web keeps the Stripe wording — the sheet's «om du ikke avslutter før {forsteBelastning}» (`passVilkaarProve`), the card's «Første belastning {forsteBelastning}» (`renewsOnEtterProve`) — because Stripe charges at `trial_end`.

**A RevenueCat billing problem is two events, and only one may write.** A failed renewal fires `BILLING_ISSUE` *and* a `CANCELLATION` with `cancel_reason = BILLING_ERROR`, generated together (RevenueCat documents the pair, and that arrival order is not guaranteed). Only `BILLING_ISSUE` carries `grace_period_expiration_at_ms` (documented); the CANCELLATION has just `expiration_at_ms`, the period's own expiry, which has already passed when the pair is sent (RevenueCat's sample `BILLING_ISSUE` shows it five hours before the event time — the docs do not show a `BILLING_ERROR` cancellation, so check a real pair in RevenueCat's event history the first time one occurs). Until Nov 2026 the webhook mapped that CANCELLATION like a voluntary one («auto-renew off, access to the period end»), and Apple's grace period was lost in **both** orders: BILLING_ISSUE first → the grace end was overwritten with a past date, so the customer lost Premium the moment the grace period began; CANCELLATION first → it moved the ordering mark (`rc_event_timestamp_ms`) past the BILLING_ISSUE generated a moment earlier, which the stale-event guard then dropped. `mapRevenueCatEvent` now ACKs it (`BILLING_ERROR_CANCELLATION_ACK`) — an ACK writes neither the row nor the ordering mark, which is what makes the two orders converge — and `BILLING_ISSUE` owns the state (grace period → access to its end; none → `past_due`) until `RENEWAL` or `EXPIRATION` settles it. `BILLING_ISSUE` with a grace period keeps `trialing` when `period_type` is `TRIAL`: the first charge after a trial failed, no money has moved, and `active` with a running period is «betalende» in the daily report. The route tests replay each chain against one row in both orders (`src/app/api/revenuecat/webhook/__tests__/route.test.ts`), including the two rules a change here must never weaken: a manual grant is a floor no store event can lower, and a voluntary CANCELLATION during a TRIAL keeps `trialing`.

**Calls out of the billing handlers have deadlines, and «no answer» is never read as an answer.** The Stripe SDK waits 80 s per attempt with one retry, and Supabase Auth's admin API waits until the platform kills the function — long after Stripe or RevenueCat has given up and queued the event again. The Stripe webhook passes `STRIPE_KALL` (10 s, one retry) on every Stripe API call and wraps `auth.admin.getUserById` in `medFrist` (`OPPSLAG_FRIST_MS`, 8 s). **Never put `sendEpost` under `medFrist` or any deadline tighter than its own** `RESEND_FRIST_MS` (15 s, roomy on purpose; it returns `{ ok: false }` on timeout and never throws): the trial-reminder mail sat under the 8 s cap, and a reminder that arrived after 8–15 s was logged as `sending_feilet`. Every other Stripe call gets a client-wide default in `getStripeServerClient` (`STRIPE_KLIENT_FRIST` in `src/lib/stripe/server.ts`: 10 s, one retry), so checkout, the customer portal and the cancellation in `/api/me/delete` (`src/lib/billing/avslutt-ved-sletting.ts`) no longer inherit the SDK's 80 s. The lookup «has this e-mail had a subscription before?» runs for every free user on every page that shows plan state, so one slow day at Stripe once held the header, the trial sheet and the pricing page for everyone who does not pay. Its deadline is part of the rule itself: `harHattTilgangFor` (`src/lib/billing/tidligere-abonnent.ts`) gives each call 4 s (`STRIPE_OPPSLAG_KALL`, no retry) and the whole lookup 5 s (`STRIPE_OPPSLAG_FRIST_MS`), then answers what a Stripe failure answers — the trial as default. `/api/billing/status` (`kanFaaProve`) and checkout both call it and each passes only a `vedFrist` callback for its own log line; the deadline first sat in the status route alone, so the surfaces promised the free week after 5 s while checkout waited for the real answer, found the old subscription and let Stripe charge the same day. Never give one of them its own deadline or its own lookup. The logged-in home page decides nothing, so it uses the display variant `provesvarForVisning` (`src/lib/billing/tidligere-abonnent-visning.ts`): the same rule (it calls `harHattStripeAbonnementFor` through a wrapped client — never write the customer loop a second time), one 2.5 s deadline (`VISNINGSFRIST_MS`) with a per-request Stripe timeout and no retries, and three answers, `'ny' | 'tidligere' | 'ukjent'`. Only `'ny'` may promise the free week (`kanLoveProve`); on `'ukjent'` the premium card shows a neutral button, because guessing the trial there could promise a week checkout then refuses. No cache on either path: a remembered «no» would promise the week to someone who has just bought, deleted the account and signed up again. `maxDuration` is the net under the database calls: 60 for the Stripe webhook, 30 for RevenueCat's (RevenueCat disconnects after 60 s), 15 for the status route. A missed deadline must land where a failure already lands, and that exposed one failure that landed wrong: the Stripe webhook's `brukerFinnes` answered «deleted» on *any* error, and «deleted» cancels the customer's running subscription at Stripe. auth-js returns network failures, 429 and 5xx in `error`, so a short Supabase Auth outage during a renewal would have cancelled a paying customer. Only an explicit 404 is «deleted» now — stricter than `erForbigaaendeAuthFeil`, because 401/403 mean *we* could not ask, not that the user is gone — and everything else goes the normal path, where a truly deleted user fails loudly on the foreign key and Stripe retries. Error bodies follow the same line: `/api/billing/status` never returns exception text and localizes its error (the pricing page shows it to the customer), the Stripe webhook returns the text only once the signature is verified, and RevenueCat's catch is only reachable after authorization. Still open: the surfaces and the purchase make separate lookups at separate times, so on a day when Stripe answers one in time and the other too late they can still disagree (worst case a returning customer is promised a week checkout does not give; Stripe's payment page shows what is charged today before they confirm); and the Supabase database calls have no per-call deadline — that belongs in `createAdminClient` (a `fetch` with a timeout), not in every caller. `docs/payment-model.md` lists every deadline by where it is set.

**Billing/capabilities** (`src/lib/billing/`). `getBillingCapabilities(subscription)` derives `{tier, status, paid, aiDailyLimit}` from the `billing_subscriptions` row (or null). Routes that gate features call this — see `src/app/api/identify/route.ts` and `src/app/api/prediction/route.ts` for the pattern. Free users get capped/coarsened data, paid users get full detail.

**Prediction endpoint** (`src/app/api/prediction/route.ts`) has two paths:
1. **Primary:** query `prediction_tiles` table via the `get_prediction_tiles_in_bounds` RPC. Tiles are generated nightly by `/api/cron/generate-tiles?country=NO|SE` (schedules in `vercel.json`, 01:15/01:45 UTC).
2. **Fallback:** when no tiles exist for the date/area, computes a score from `fetchWeatherSummary()` + historical findings. Returns 502 if no weather provider is reachable for the region.

When `?speciesId=N` is set, the route applies a per-species multiplier from `src/lib/utils/species-scoring.ts` to the final score (see "Per-species scoring" below).

**Weather adapters** (`src/lib/weather/index.ts`). Single export `fetchWeatherSummary({lat, lon})` that routes by region:
- `'NO'` → MET Norway Frost (requires `MET_FROST_CLIENT_ID`; placeholder is a no-op stub)
- `'SE'` → SMHI Open Data (no key required)
- `'other'` → OpenWeather (requires `OPENWEATHER_API_KEY`)
- Returns `null` if no provider is configured/reachable for that region.

Region detection in `src/lib/utils/region.ts` — bounding-box check, returns `'NO' | 'SE' | 'other'`.

**Three distributions, one 0–100 label.** The same-looking score has different distributions depending on the surface, and each needs its own ladder. A raster *cell* (`cell-score.ts`) is graded by `CONDITION_THRESHOLDS`; a *region* on `/soppforhold` is the 90th percentile over cells and is graded by `REGION_CONDITION_THRESHOLDS` (`src/lib/prediction/region-score.ts`), measured at p90/p75/median of 374 real region-days; the *point day-score* from `mushroom-day.ts` has its own `forecast-scale.ts` bands. Mixing them is a real bug that shipped: the region endpoint reused the per-cell ladder, so a verdict promising "top 10%" fired on 22.5% of region-days, and the colour came from a third ladder entirely — the same number could get the peak verdict in text and an amber dot beside it. Recalibrate with `npm run calibrate:regionterskler` after the season; the current basis is a 17-day August window. The alert threshold (`VARSEL_MIN_SCORE` in `src/lib/alerts/decision.ts`) is bound to the region ladder's `excellent` for the same reason: it used to import the point-scale `FORECAST_GREEN_MIN` (85), which on the region distribution is the top 12 % of days — 7 of 22 regions (Oslo, Stockholm) never reached it in a month, so alerts and X posts were silent in the biggest markets. The Sunday X post (`byggUkesPost` in `src/lib/x/innlegg.ts`) reads the same ladder the other way: it stays silent when the best region is under `moderate` (the median region-day). Its only condition used to be a non-empty list, so «best an ligger Bergen (4 av 100)» went out every Sunday all winter. The middle rung's *words* follow the season, never its threshold: `scoreVerdict` and `buildSpotSummary` (`src/lib/utils/prediction-explanation.ts`) and the map's `HotspotPanel` say «så vidt i gang» / «precis i gång» while the season rises or peaks, and «fortsatt i gang» / «fortfarande i gång» from October through March (`etterToppen`, derived from the `sesongtilstand` phases: the last high-season month, `ettersesong` and `vinter`). With one wording all year, the home card's regions block said «så vidt i gang» under «sesongen er på hell» in November, and the map panel said the opposite of the cell tooltips on the same map. Ladders, thresholds and dot colours are unchanged; `scoreVerdict` takes the month as an optional fifth argument and otherwise uses the current Oslo month.

**One season state** (`src/lib/sesong/sesongtilstand.ts`). `sesongtilstand(naa)` is the only answer to «where in the mushroom year are we?»: Oslo time, the date injected, phases `forsesong` (Jun–Jul), `hoysesong` (Aug–Oct), `ettersesong` (Nov), `vinter` (Dec–Mar), `var` (Apr–May). Before it no surface knew what month it was — in November the pricing page said high season was under way, the trial sheet sold «resten av høsten», the home card told people twice to come back in late summer, and `/soppforhold` wrote that a species «er i sesong her nå» beside 3/100. Four rules. (1) It is the **calendar, not the conditions**: a dry August is still `hoysesong`, so a surface that says something about conditions must also read the numbers (`innledningsTilstand` in `src/app/soppforhold/hent-regioner.ts` requires both low scores and `!iHovedsesong` before it says «utenom sesongen»). (2) **«Hovedsesong» is the code's word, not the copy's.** `iHovedsesong` means June–November (season weight above zero), but to the user «hovedsesong» / «högsäsong» means August–October — the tick «Hovedsesong for sopp i Norge» first appears on 1 August. The off-season text once pasted the constant's name into the copy and told Swedish users «Högsäsongen börjar i juni». Write «soppsesongen starter i juni, med høysesong fra august», and use `erHoysesong` for what the user calls hovedsesong. (3) Off-season copy has one source, `src/lib/sesong/utenom-sesong-tekst.ts` (two copies rendered the same sentence twice in one card for half the year), and it never says «kom tilbake» — that is telling people who paid for a year to leave. (4) The month table is written out rather than imported, because the file is used in client components (pricing, trial sheet); `sesongtilstand.test.ts` locks it to `SEASON_WEIGHT_BY_MONTH` in `mushroom-day.ts` for all twelve months. «Is this species in season?» is a separate question with its own single answer, `erArtISesong` (`src/lib/sesong/art-i-sesong.ts`): the calendar's window (`baseSeasonMask`), with `null` meaning unknown, not «out». The regions endpoint used the narrow catalogue months alone and said «utenfor sesong» about the species the raster itself ranked first (piggsopp in August), so `/soppforhold` dropped the species line in mid-season. Purchase surfaces take their season lines from `src/lib/billing/sesongtekst.ts`, which returns keys only for the months the claim is true. The claim of promising areas there follows `lovendeLofte()`, gated by the **Oslo month**, not by `iHovedsesong` or the phase: `'naa'` July–October, `'betinget'` November–June. The trial sheet sold «Alle 12 lovende områder nær deg» all year, but ⭐ Lovende shows only cells from `CONDITION_THRESHOLDS.moderate` (50) — for paying users too — and the grid scores without finds history, so a cell gets at most 50 from its environment plus `computeSeasonalScore`'s 15 (Aug–Oct), 10 (Jul, Nov), 5 (May–Jun) or 2: from December to April almost nothing qualifies, November needs a mild and very wet day, and June scores exactly like May (a plain spruce forest needs ≥ 12 mm over three days and 80–85 % humidity there, while July reaches 50 on ordinary wet weather). On `'betinget'` the sheet (`ProvGratisArk.tekstStartBetinget`) says in the map's own words that from November to June conditions are often too weak for the map to call anything promising, and the Premium bullets (`Home.premiumFeatureFullPrediction`, `Pricing.premiumFeature2`) add «når forholdene tillater det»; the `begrenset` trigger (after a free ⭐ Lovende search) has its own text, which states limits and never a count — «Gratis viser opptil 3 lovende områder. Sesongpass og Premium viser opptil 12 i et finere rutenett» — and takes its title from the plan like the other triggers, so it needs no season switch. It said «Se alle 12 lovende områdene — Gratis viser 3 … alle 12» on the premise that it shows only after the map has shown promising areas, but the trigger fires on one area or more, and the grid picks its top 3 (free, 5×5) or top 12 (paid, 7×7) over the whole box before the client drops what lies outside the radius (4 of 25 and 12 of 49 cell centres): even when every cell qualifies, free shows all 3 in only 58 % of searches and paid all 12 in 2 %. **The home card's day verdict and flush banner read the same gates** (`assessMushroomDay` in `src/lib/prediction/mushroom-day.ts`, `assessFlush` in `flush.ts`; `/api/mushroom-forecast` assembles them as `buildWeek` → `assessFlush` → `reconcileFlushWithWeek`). They sit directly above each other and come from different models: on 16 Nov 2026 a yellow 69 «ikke helt optimale» sat over a green «Forholdene er modne nå 🍄 … Ta turen ut!», and because the score gives temperature points up to 22 °C while the banner called conditions ripe only at 3–20 °C, a 21 °C August day could put «🍄 Perfekt soppdag i dag!» over «Tørt — soppen venter på regn — Lite fukt» (reproduced, score 90). Three readings in `mushroom-day.ts` are now shared: `seasonShoulder(month, dayOfMonth)` (`'late'` = all of November, phase `ettersesong`; `'early'` = June and 1–14 July, phase `forsesong` while the smooth season weight is under July's 22 — late July keeps the peak words on purpose); `flushTemperature` (`'cold' | 'mild' | 'warm'` against the 3–22 °C band — the warm edge is the score's own: at 20, Sweden's input, SMHI's latest hourly reading rather than a daily mean, flipped a wet August day from «Perfekt» at 07:00 to «too warm today» 13:00–18:00 and back at 21:00 (reproduced), while the score and the bolete optimum (15–22 °C) called that warmth fine); and `isWetForFlush` (soil index ≥ 0.55, or without an index the banner's 7-day rain proxy, rain7/25). The optimal gate requires the band, so a celebrated day is always one the banner calls ripe (without a soil index the banner's rain proxy could still say dry, so there it follows the verdict's `dayOptimal`). Outside the band an explained verdict says «For varmt/kaldt for sopp akkurat nå» (not «i dag», since the reading can be a single hour) and nothing about the soil, and moist soil gets the grey banner «Fuktig, men varmt/kaldt — soppen venter på kjøligere/mildere vær» (status `dormant`, reason `warm` | `cold`), never «Tørt — Lite fukt» or «Regn på vei». In a shoulder the banner's `fruiting` gets early or late words without 🍄 unless the verdict is optimal (the route passes `dayOptimal` and the Oslo `dayOfMonth`); November's `building` and `soon` get late words too, since their projections land in December; such banners carry `shoulder`, `flushTint` in `MushroomDayCard` makes a qualified `fruiting` amber, and `reconcileFlushWithWeek` keeps a late banner's words and appends the week's best day only while that day is still in season. In a shoulder the verdict's dry-soil and little-rain texts have their own versions (the plain ones say «Vær og sesong er på plass» / «Temperatur og sesong stemmer», and the dry-soil one promises mushrooms 1–2 weeks after rain — in late November that is December), and «Fuktig nok — men det er tidlig i sesongen / sesongen er på hell» appears only when the season weight costs at least as much as each weather factor and the banner's wetness test agrees. Beyond the words, the score and `optimal` are unchanged: `mushroom-day.test.ts` locks both against a verbatim copy of the old formula — without temperature points the score tops out at 80, and it gives none outside 6–22 °C, so the band in the gate excludes no day the old formula celebrated; the banner's ripe band now reaches 22 °C instead of 20. `src/lib/prediction/__tests__/dom-banner-matrise.test.ts` builds 1,072,512 cards through the route's assembly and checks them against an explicit list of forbidden (verdict, banner) pairs: a new verdict or banner title must be added to its lists, or the test fails (the three older rain tensions it allows, one of them only without a soil index, are counted in its header). The 7-day strips (home card, `PlaceForecastStrip`) draw only each day's score and optimal colour, and the area pages' strip ranks bars without numbers — the per-day title and message `buildWeek` computes are shown nowhere.

**SR16 lookups are header-keyed.** NIBIO's GetFeatureInfo omits a layer's whole sub-document when it is nodata at the pixel (it does not return −9999), so a positional parse shifts every later value — the original parser read standing volume as site index in 0–14 % of forest cells, which cleared the rich-soil bonus and corrupted the soil factor in the nightly tiles. `parseSr16Html` keys on the «Skogressurskart (<LAYER> raster)» headers (normalising NIBIO's `SSRVOLMB` typo). Cells with treslag nodata but bonitet/volume present are forest and are kept as `ukjent`. Background and the patch-level signal study: `docs/mikro-prediksjon-gjennomgang.md`.

**Forest is sampled at up to five points per grid cell.** SR16 and CORINE are point lookups, and every grid — the nightly raster, `/api/prediction/grid` and `/api/prediction/species-spots` — used to look up only the cell centre and drop the whole cell when that point was water, a field, a road or a settlement, leaving holes over forested land (Oslo map, 15 Sep 2026: Nesodden's east coast, east of Lørenskog, around Enebakk). All three now go through `provSkogIRuter` (`src/lib/prediction/skogprover.ts`): every centre first, then for misses the four quadrant centres (±step/4) in fixed order, first hit wins; cells with no forest at any of the five points stay honest holes (lakes, the fjord, city centres). The cell keeps its centre — grid position, score inputs and pin are unchanged; only the forest data comes from the offset point, which tiles record as `metadata.skogprove` (`senter` | `forskjovet`) + `skogprove_lat`/`skogprove_lng` and which `nearestForestTile`, the grid's area report and the pin explanations in both live grids use for the distance. The pin text must get `skogavstandKm(cell, prove)` — null only when the forest was measured at the centre, because `null` is what prints «Skog her» (and `0` would print «0 m unna»); a live-grid quadrant centre is several km from the pin. Measured live with `npm run dekning:rutenett` (no writes): Oslo 53 → 76 of 84 cells, Bergen 16 → 35 of 40, all of Norway 181 → 317 of 399, Sweden 219 → 354 of 420 uncapped. Offsets run in rounds (first quadrant for every miss, then the second…) so a cap spreads over the region instead of being spent on the first cells and on lakes. They are bounded per region by `EKSTRA_SKOGOPPSLAG_PER_RUTE` (no real cap for SR16; 0.65 per cell for CORINE, which is ~10× slower — ~99 of Sweden's 135 recoverable cells) and by a deadline that reserves time for the remaining regions' centres (`skogproveFrist`); cells cut short are logged as `generate_tiles.skogprove_avkortet`, never dropped silently. The live grids stop starting offset lookups 6 s into the forest phase, so a struggling NIBIO is not hit four times harder.

**Per-species scoring** (`src/lib/utils/species-scoring.ts`). **Visibility model for findings.** `findings` rows have `visibility` (`public` | `approximate` | `private`) and an `is_zone_finding` flag. The `set_display_location` trigger computes `display_latitude/longitude` based on those fields — randomized for `approximate`, grid-snapped for zone findings, NULL for private. Views like `public_findings` and APIs use the display columns, never raw `latitude/longitude`. If you change visibility logic, update the trigger, the view **and** `src/lib/findings/delingsendring.ts`, whose planner mirrors `set_display_location` (a test there models the trigger line by line). Two migrations guard the stamp. **042** freezes it on update — without it every update of an approximate find (a corrected note, a restore) draws a new random point, and the mean of N points converges on the real spot. **075** fixes the zone stamp: until it, the longitude step was computed from the find's *exact* latitude, so `display_lng · 111.32 · cos(display_lat) / p` gave back the exact latitude from one public row (checked for 20 000 Nordic points); 075 derives the step from the snapped latitude (`zone_grid_location`) and re-stamps existing zone rows. Both replace `set_display_location`, so **042 pasted after 075 brings the leak back**; the tripwire advice (`JITTERVAKT_TILTAK` in `src/lib/findings/jittervakt.ts`) names 075 for that reason. Until 075 is pasted, `POST /api/findings` guards new zone finds itself (`src/lib/findings/sonevakt.ts` + `sonerute.ts` — the code cannot ask the database whether 075 ran, but it can see what the trigger stamped): the insert reads `display_*` back, and for a zone find that is not private a point that does not match 075's `zone_grid_location` (within `SONERUTE_TOLERANSE_GRADER`, 1e-9°) means the old trigger is installed. The row is then made private at once (owner-scoped, and confirmed to come back private with null `display_*`), or deleted if that fails; the answer carries `notice: { code: 'zone_saved_private', message }` (`FUNN_BESKJED` in `src/lib/findings/feil.ts`) or the error `zone_not_saved`. Each step counts as done only when no failure was recorded, and any error object is a failure, also one with an empty `code`: supabase-js does not throw when a request fails in transit — postgrest-js resolves it with `error.code === ''` (an error response with no JSON body gives `{ message: '' }`) — and the first version (`error.code ?? …`, then `if (!privatFeil)`) took that empty string for success and answered `zone_saved_private` while the row stayed public. `sonevakt.test.ts` runs the guard against the real postgrest-js client with a fake `fetch` for that reason. With 075 in place the guard does nothing; if 075's formula ever changes, change `sonerute075` too (`sonerute-migrasjon.test.ts` ties them). A successful `POST` may carry such a `notice` in the reader's language: clients read it (`lesLagreSvar` in `src/lib/findings/funn-kall.ts` on `/identify/result`, `lagringsBeskjed` in `src/lib/map/funn-svar.ts` in `AddFindingSheet`) and show it instead of the plain success toast.

**Own finds can be edited, under a quarantine** (`PATCH /api/findings/:id`, `POST /api/findings/:id/restore`, `/mine-steder`). The owner can change sharing, species and note of a non-deleted find and restore a soft-deleted one within `PURGE_AFTER_DAYS` («Nylig slettet»). The owner's map popup links to `/mine-steder?funn=<uuid>`, which opens the place card holding that find and marks it (`apneFunnId` in `StedetsFunn`); only the id goes in the URL. `parseFindingPatch` (`src/lib/findings/request.ts`) is a whitelist — position, `display_*`, image URLs, `found_at` and `ai_*` are rejected — and the response never carries the note or coordinates. Read, compare, then write: a patch that changes nothing must not reach the database, because every UPDATE sets `updated_at`, which is the quarantine clock. The rules (`planleggFunnEndring` in `delingsendring.ts`, shared by the route and `EndreDelingArk` so the sheet shows the rule before the tap): making a find private always works; exact → approximate always works; anything that puts out *something new* — a new random point (private or zone → approximate) or the exact point — waits until the find has stood untouched for `DELING_KARANTENE_TIMER` (24 h), unless it was never updated, and answers 429 `sharing_cooldown`. It is a brake (one new point per find per day), not a lock; the lasting fix is a migration that stores the first jitter point. Turning a find *into* a zone is closed (503 `zone_unavailable`, and the sheet does not offer it) while `SONE_OMGJORING_AAPEN` is false — the code cannot see whether 075 has been pasted, and a test fails if the flag is set to true before the ledger row for 075 reads «kjørt». The zone size can never be changed after saving — the planner answers 400 `zone_size_locked` for any new size, with or without 075: cells of different sizes do not share east–west edges, so two sizes of one find narrowed it under 500 m for about 1 % of finds and all fifteen slider values for over half — with position and size both locked a find has exactly one cell for life. The tripwire for a missing 042: PATCH and restore compare `display_*` before and after an update that should not move the point; if it moved, the instance logs `findings.jitter_guard_missing` and answers 503 `guard_missing` to further note/species edits on approximate finds until it restarts (making a find private is never blocked). Every `/api/findings` route answers `{error, code}` in the reader's language from `src/lib/findings/feil.ts` via `src/app/api/findings/svar.ts`; clients branch on `code`. `unauthenticated` there repeats the text of the server-only `src/lib/api/feil.ts` (which reads cookies, so the pure findings module cannot import it), and a test keeps the two equal: one code, one text — «Du må være logget inn.» / «Du måste vara inloggad.» — except in `/api/identify` and `/api/identifications/[id]`, which still have their own «Ikke autentisert» tables. A missing column arrives as 42703 from a filter and as PGRST204 from a write — use `erManglendeKolonne`. All of these are writes against production: unit tests with a mocked fetch, manual checks in the QA checklist, never the authed e2e project.

**Where a find is saved.** `AddFindingSheet` takes no GPS prop: it measures the position itself when it opens (`finnFerskPosisjon`, `src/lib/map/fersk-posisjon.ts`), always gets the map centre too, and `velgFunnposisjon` (`src/lib/map/funnposisjon.ts`) picks — fresh GPS when the map stands where the app put it (`autoSenterRef` / `kartErFlyttet`; «⭐ Lovende» records the centre it fits the map to with `senterForBoks`) or when GPS and map centre agree within `SAMME_STED_M` (150 m); otherwise the user must choose and «Lagre» waits. The app never chooses silently between two different places. Before, «GPS wins» used the fix from when the map was opened, so a find was saved at the car park after a forty-minute walk, or at home when the user had moved the map to yesterday's clearing — wrong data in the user's own places and in what the model is calibrated against. Two gotchas behind it: `useGeolocation()`'s latitude/longitude are measured once at mount and never updated (use `sisteGpsRef` in `MushroomMap`; `posRef` is also set by place search, so it is not the user either), and `@capacitor/geolocation` ignores `maximumAge` on iOS while CoreLocation hands out its cached last-known fix first, often with good accuracy — anything that needs «here and now» goes through `finnFerskPosisjon`, which filters on the fix's timestamp (`FERSK_MAKS_ALDER_MS`) and has a separate, longer deadline while the permission dialog is open. **Finds saved from `/identify/result`** follow `src/lib/findings/resultatposisjon.ts`: the page always shows which position will be saved and how old it is; the identification's position is used without asking only while it is fresh (`FERSK_IDENTIFISERING_MS`, 10 min), and anything older or of unknown age must be chosen — that position, «der jeg står nå» (measured with `finnFerskPosisjon`) or the map. EXIF is never read (it is stripped before upload). The result used to be saved wherever the identify page had measured, unseen, so a photo taken in the forest yesterday and identified from the sofa became a find at home. The age is the fix's own: `getOptionalPosition` (`src/lib/hooks/useGeolocation.ts`) returns a `MaaltFix` whose `timestamp` is ms since the epoch on every platform (`GeolocationPosition.timestamp` in the browser, CoreLocation's or Android's fix time through the plugin), and the identify page stores it as `payload.location.timestamp` via `medPosisjonstid` (`src/lib/identifications/okt-resultat.ts`), capped at the device time the position arrived, because a GPS fix can carry satellite time while the phone's clock runs slow. Without it (older sessions, a platform with no timestamp, the history) the page counts from when it first read the result (`posisjonSettMs`) or from the history row's `createdAt` (`?id=`) — only lower bounds (`erOmtrentligMaaletid`), and the copy says so; with it, the copy describes the measurement («Posisjonen telefonen målte {age}», «Der telefonen målte posisjonen»), never the press on «Identifiser», since a cached iOS fix can be far older than the press. `getCurrentPositionOnce` and `getCurrentPositionIfGranted` still return coordinates only.

**The finds layer is reconciled, never cleared and rebuilt** (`Funnlag` in `src/components/map/funnlag.ts`, rule in `stemAvFunnlag`, `src/lib/map/funnlag-avstemming.ts`). Clearing a marker cluster group closes the open popup, and every map move triggers a fetch — including the pan Leaflet does to fit a popup — so the delete confirmation and the report form vanished under the user's finger. Markers for finds still in the answer stay; only what is gone comes out and only what is new goes in. A popup is re-rendered only when its `signatur` changes, so anything that changes what a popup shows must be part of the signature. Report and block live in that popup, which is a detached React root with next-intl but no QueryClient: the map owns the calls and throws `VisbarFeil` (`src/lib/map/visbar-feil.ts`) carrying catalog text or the findings routes' localized `error`. The popup shows a thrown message only when it is marked that way (read as a field, not with `instanceof` — popup and map can hold separate copies of the module) and otherwise its own catalog text, because a `fetch` that fails without coverage throws the browser's English «Load failed». Never throw a plain `Error` with user-facing text to the popup. `serverFeiltekst` (`src/lib/map/funn-svar.ts`) trusts a body's `error` only when it carries a string `code` — the findings routes' shape — or, with status 429, the rate limiter's `{ error, retryAfterSeconds }` (its text says «wait», the catalog's says «try again»); a Vercel 502 page or a proxy body gets the catalog text. Blocked users' finds are filtered in the browser with `utenBlokkerte`, waiting at most `BLOKKERTE_FRIST_MS` (2.5 s, `src/lib/map/blokkerte-brukere.ts`) for the block list and taking the pins out afterwards when it arrives late. `blocked_users` has no UPDATE policy, so every block write is insert-or-ignore (`upsert` with `ignoreDuplicates: true` — `blokkerBruker` in `src/lib/hooks/useBlocks.ts` and the map's own write): a plain upsert on an existing row takes the DO UPDATE path, RLS rejects it, and a double tap told the user «Kunne ikke blokkere» about someone who was blocked. Map tap targets: controls stay small on screen and get an invisible 44 px hit area from `TREFF_44` (`src/components/map/trykkflate.ts`); the element must be positioned itself, because Tailwind emits `.relative` after `.absolute` and the two cancel.

**A user's point leaves the server rounded.** External place lookups (weather, forest, elevation) get `roundForProviderLookup(lat, lon)` (`src/lib/privacy/provider-precision.ts`): three decimals, about 110 m — still inside the box NIBIO queries with and far under the distance to the nearest weather station, so the answer is the same. `/api/findings` once passed the untouched point of every saved finding, private ones included, to MET Frost, NIBIO, Kartverket and CORINE, where a secret spot settled in four institutions' access logs; `/api/spot-feedback` was fixed in the same round, and `/api/prediction` — whose point is the device's GPS position or the map centre, often exactly where the user is standing — was the sibling forgotten until Nov 2026. The math that never leaves the server (bounding box, nearest tile, finding density) keeps the exact point, the `prediction.start` log line gets two decimals (server logs must not hold a position trail), and Kindwise gets `coarsenLocation` (`src/lib/privacy/coarsen-location.ts`, 0.1° cells) instead, because there the point is to be hidden, not merely trimmed. `/api/mushroom-day`, `/api/mushroom-forecast` and `/api/prediction/species-spots` round each outgoing lookup point; only the outgoing lookup is rounded — cells, pins, cache keys and the forest-sample distance keep exact points, and nothing is rounded inside the shared lookup functions. `/api/prediction/grid` is different on purpose: the centre of its request box *is* the device position, so `festBoksTilOppslagspresisjon` (`src/lib/map/oppslagsboks.ts`) moves the whole box so its centre has three decimals and keeps its size. Never round each grid point instead — at small cell sizes that collapses the quadrant points of `provSkogIRuter` and changes the forest sampling. The map rounds too, before anything reaches a URL: «⭐ Lovende» rounds its starting point before computing the box, and `predictionCoords` in `MushroomMap.tsx` is only ever set through `roundForProviderLookup` — it is the `usePrediction` query key, so mixed precision would also mean duplicate calls. A new route that hands a user's coordinates to a provider must round first and get an `oppslagspresisjon.test.ts` beside it, like the four routes above.

## Cross-cutting infrastructure

**Logging** (`src/lib/log/`). Five-level structured logger: `trace < debug < info < warn < error`. Default level is `debug` in dev, `info` in prod; override with `LOG_LEVEL` env. Output is pretty single-line in dev, JSON object per line in prod (Vercel/Sentry-ingestible).

Use `createRequestLogger(request)` in route handlers to get a child logger pre-bound with `reqId` (correlation ID propagated via the `x-request-id` request header set by middleware) and `route`. PII is auto-redacted — emails masked, secret-pattern keys (password/token/apikey/authorization/etc.) replaced with `<redacted>`. UUIDs and numeric IDs pass through (internal-only, useful for cross-referencing).

`Logger.error(msg, err, ctx)` takes the error second and context third, unlike `warn`/`info`, and normalises the second argument, because many call sites pass something else there and anything that was not an `Error` used to print as `[object Object]`: an `Error` (also `PostgrestError`) keeps its `cause` and the own fields on the allowlist `ERROR_FIELDS` in `src/lib/log/pii.ts` (code/details/hint, status/statusCode, errno/syscall, Stripe's type/rawType/requestId) — never the rest, because Stripe's `StripeSignatureVerificationError` carries the raw webhook body (`payload`) and the signature header as own fields, and copying every own field wrote the customer's name into the log on every failed signature check; a plain object made only of error fields becomes `err` with those fields; any other plain object passed second with no third argument is treated as the context it is. Every string is cut at `MAX_STRING_LENGTH` (4096) before the redaction patterns run, and never inside an address or a token (half of one is no longer recognised and would stand in clear): `EMAIL_REGEX` backtracks quadratically on a long run without «@», and a 100 kB body — anyone can post one to the webhook with a made-up signature — kept the event loop busy for 12 s when measured. In API routes `loggFeil` (`src/lib/api/feil.ts`) is still the preferred form.

See `docs/logging.md` for the full conceptual model + the documented Next 14+ quirk where middleware-set response headers don't propagate to the client (only the request-header rewrite half works; server-side correlation is unaffected).

**Audit log** (`src/lib/audit/log.ts` + `admin_audit_log` table from migration 008). Append-only by trigger — UPDATE/DELETE blocked at the DB layer even for the service role. Use `logAdminAction({actorId, action, targetUserId, metadata, request})` for compliance-relevant events: admin role changes, account deletion, etc. Currently wired into `/api/admin/verified-foragers` (POST + DELETE), `/api/admin/moderation` (every action, as `moderation.<action>`) and `/api/me/delete`. The helper is failure-safe — if the service role key isn't set or the migration isn't applied, the underlying action still succeeds and a warning hits the server console.

**Forum moderation** (`/forum/moderation` → `GET`/`POST /api/admin/moderation`, pure logic in `src/lib/moderation/moderering.ts`). Until Nov 2026 a moderator could only change a report's status: the console never showed what was reported, and nothing in the app could hide a post — the only UPDATE policies on `forum_posts` and `comments` are owner-only, so dangerous advice about a deadly look-alike could be removed only with hand-written SQL, while Apple (guideline 1.2) expects a report to be acted on within 24 h. The route checks `moderator_roles` with the session client (a failed lookup is «no») and does the work with the admin client, because hidden rows — and rows by authors the moderator has blocked — are invisible through RLS. `POST` takes only `{reportId, action}`: the target is **always derived from the report row on the server**, never from a client-supplied table or id, so the route cannot be used to hide arbitrary content. Actions: `hide` (sets `is_hidden`, resolves every open report on that content), `unhide` (shows it again and sends the reports the hide had resolved back to `reviewed` with `resolved_at` cleared — that date drives deletion a year later), `dismiss`, `reviewed` (seen, still open) and `resolve` (handled without hiding — the only way to close a finding report other than dismissing it). «Open» means `pending` **or** `reviewed` (`AAPNE_RAPPORTSTATUSER`) on every surface: the console's list and banner, what a hide resolves, the `/admin` card and the daily report; counting `pending` alone made a report vanish the moment someone had looked at it. **Findings cannot be hidden**: `findings` has no `is_hidden`, and `deleted_at` is the owner's own 30-day undo (the purge cron hard-deletes the row and its image), so it must not be borrowed for moderation — removing a finding needs a migration (`is_hidden` plus the `public_findings` view). What never leaves the server (`byggRapportvisning` builds each object field by field): `reporter_id`, finding coordinates raw or masked, and, for a finding, anything `public_findings` would not show its readers — the reports table does not check that the reporter could see the finding, so an id from a linked post must not become a way into someone's notes. There is no way to eject a user yet; that needs an owner decision. **Notification:** a new report used to be seen only by whoever opened the console. Nothing fires when a report is filed (the insert is client-side, `useReportContent` in `src/lib/hooks/useForum.ts`), so notice is e-mail on a clock, twice a day and twelve hours apart: the daily report (06:00 UTC: subject line, a banner above the numbers and a row, as soon as *anything* is open) and a quiet evening slot, `/api/cron/aapne-rapporter` (18:00 UTC), which mails only when something is open — and mails «ikke målt» and answers 500 when the read fails, because silence in the evening means «nothing waiting». With the daily report alone the first notice could come 23 h 50 min after the report was filed, i.e. the whole deadline; now it comes within 12 h. Both read `hentAapneRapporter` (`src/lib/rapport/aapne-rapporter.ts`, one read-only query: count and oldest `created_at`, nothing about content or reporter) and take their words from `src/lib/rapport/modereringsvarsel.ts`: the clock time the deadline runs out in Europe/Oslo, «nå» when the next notice would come too late (after the deadline, or with less than `HANDLINGSROM_TIMER` = 3 h of it left), red only once it is over, and «nå» for an unreadable age. `VARSELINTERVALL_TIMER` (12) is bound to the two schedules in `vercel.json` by a test — move a slot and the «nå» rule must move with it. A report left in `reviewed` keeps producing the evening mail until it is resolved or dismissed. The `/admin` card and the console's banner (`GET /api/admin/moderation`) count through the same `hentAapneRapporter` and summarise with the same `oppsummerAapneRapporter` and `BEHANDLINGSFRIST_TIMER`, so console, card and e-mails cannot disagree. When the count fails, the route answers `pending: null` and the console says «ikke målt», never 0 — «0 åpne» hid the banner and the 24 h warning exactly when nobody knew whether something had waited too long. Two smaller forum rules from the same round: readers of `public_findings` filter blocked authors with `utenBlokkerte` (`src/lib/moderation/blokkering.ts`) because the view does not know the block list that RLS applies in the forum, and a post's linked finding is read through `public_findings` (`hentKobledeFunn`), never embedded from `findings` — owner-only RLS returned `null` to everyone but the author, who could not tell. The forum's «Moderasjon» link comes from `useErModerator` (`src/components/forum/useErModerator.ts`): the session is read locally, so logged-out readers make no request and logged-in ones one own-row lookup per session; it is display only — access is decided on `/forum/moderation`. Posts and comments are dated through `forumDato` / `forumTidspunkt` (`src/components/forum/forumDato.ts`): fixed Europe/Oslo zone, explicit locale, the year always shown (a find reported last year is different news) and no relative times, so server and browser render the same day. The counters on posts are trigger-kept — see «Trigger functions that write elsewhere» under Database notes.

**Rate limiting** (`src/lib/rate-limit/`). In-memory fixed-window token bucket. Use `checkRateLimit(key, limit, windowSeconds)` + `getClientKey(request, userId)` + `rateLimitResponse(result)` from `src/lib/rate-limit/route`. Applied in about 40 route handlers (`grep -rl checkRateLimit src/app/api`), e.g. `/api/identify` (20/min/user), `/api/prediction` (60/min/client), `/api/billing/checkout` (5/min/user), `/api/me/export` (10/min/user), `/api/me/delete` (5/min/user). **Per-instance only** — Vercel auto-scales horizontally, so effective limit is `N × configured`. The app is live with this limiter; replacing it with Upstash Redis or Vercel KV is still an open follow-up. `refundRateLimit(key, taken)` gives a slot back, for a caller that must reserve before the work (so a concurrent burst cannot all take the last slot) but should only be charged when the guarded thing happened.

**Localized API errors** (`src/lib/api/feil.ts`, server-only). `apiFeil(code, status, {locale?, detaljer?, hint?})` answers `{ error, code, details?, hint? }` from one nb/sv table; it takes a code, never free text, so a database or provider message cannot reach the browser through it. Clients branch on `code`, never on the text. A new error is a new row with both languages (`feil.test.ts` fails otherwise). Log Supabase errors with `loggFeil(log, event, error)`, which keeps code, message, details, hint and status (see Logging for what `log.error` does with the rest). `src/lib/api/__tests__/ruter-svarer-oversatt.test.ts` scans every `route.ts` for `error:`/`details:` followed by a string literal or `<x>.message`; its exemption list (`UTENFOR`: cron, the two webhooks and health) must shrink, never grow — `findings/` and `billing/status/` (which localize through their own tables) and `admin/moderation/` (now `apiFeil` with `moderation_*` codes) are guarded too — and a false positive (a log context key named `error`) is fixed by renaming the key. In the browser, never print `err.message` from a catch around `fetch` — it is the browser's own English («Load failed», «Unexpected token <»); hooks that read our JSON use `.json().catch(() => null)` and treat «not OK» and «not JSON» alike, because a platform 504 is an HTML page. Two related helpers: PostgREST's `.or()` takes the whole filter as text and supabase-js does not escape it, so search text goes through `filterVerdi()` / `inneholderMonster()` (`src/lib/api/postgrest-filter.ts`) — `*` stays a wildcard in like/ilike, PostgREST has no literal for it; and «today» for a reader is the Oslo date, `osloIDag()` (`src/lib/api/oslo-dag.ts`, built on `sesongtilstand()`), used by `/api/mushroom-day` and `/api/mushroom-forecast` for date and cache key (tile dates stay UTC on purpose — `generate-tiles` writes them with the UTC date). The routes that decide month or season — `/api/prediction` and its `species-spots` and `grid`, `/api/identify`, `/api/identifications/[id]` — read the Oslo month the same way (and `osloDagIAaret` for the phenology curves), never `new Date().getMonth()`: on a UTC server 1 June at 00:30 was still May, and May is off-season; `src/lib/api/__tests__/oslo-maaned-i-ruter.test.ts` holds them to it. A client cache keyed on a route's «today» uses the same Oslo date (`osloIDag(...).dato` or `sesongtilstand().osloDato`), never `toISOString().slice(0, 10)` — the home card keyed its cached forecast on the UTC date and could draw yesterday's strip as «I dag» for an hour or two after midnight. Tests for that class must set `process.env.TZ = 'UTC'` (pattern: `src/app/api/mushroom-day/__tests__/oslo-dato.test.ts`), because on a machine in Oslo `getMonth()`/`getDate()` give the right answer by coincidence.

**Mushroom alert (soppvarsel): links, gaps and the signup throttle.** Mail scanners fetch every link in an e-mail within seconds, so `/api/soppvarsel/av` (unsubscribe) and `/api/soppvarsel/bekreft` (confirm) write on GET only for a real browser navigation (`Sec-Fetch-Dest: document` + `Sec-Fetch-Mode: navigate`, `hvorforIkkeNavigering` in `src/lib/alerts/lenkeside.ts`), and unsubscribe also waits `AKTIVERING_MIN_MS` from the send time carried in the link (`&s=`); anything else gets a one-button POST page rendered without looking the token up, and HEAD never writes — the same pattern as the trial-answer links. Confirm has no time window on purpose. RFC 8058: any POST to `/av` without `skjema=1` is one-click (200, no redirect), and the `List-Unsubscribe` header keeps the plain URL without `&s=`. A hole in `region_daily_scores` is **bridged, never filled**: `lesRegionHistorikk` (`src/lib/alerts/historikk.ts`) treats up to `MAKS_HULL_DAGER` (2) unmeasured days as bridgeable for both «yesterday» and a flip, above → above across a hole is never a flip, and the table must never be backfilled with interpolated scores (calibration reads it). The X post cron reads the history through the same function (`lesOmslagsgrunnlag` in `src/lib/x/innlegg.ts`) so it fires on exactly the mornings the e-mail does; a flip found across a hole is `brobygd`, and no text built from it — X post or the owner's press pitch (`src/lib/alerts/presse.ts`) — may say «i natt». The X cron reports a flip only when `region_daily_scores` has today's `tile_date` (UTC, as the tiles are dated); its one-day freshness slack serves only the Sunday summary — a night without new scores used to re-read yesterday's numbers and post the same flip verbatim again, with a new press alert and a second row in the public fasit log. One scale per alert e-mail: the outlook line names days, never a number (`Toppdag` in `src/lib/alerts/ekstra.ts` has no score). **Double opt-in lives in the alert cron alone** (it reads with the admin client, so RLS does not apply): an e-mail row without `confirmed_at` never gets an alert, while account rows pass on `user_id` — 057 backfilled `confirmed_at` only for the account rows that existed then, and `/api/me/soppvarsel` never sets it, so simplifying the gate to `!ab.confirmed_at` would silence every account row created since. `src/app/api/cron/soppvarsel/__tests__/route.test.ts` runs the whole route against a fake PostgREST that returns only the selected columns, evaluates the claim's `or()` quarantine filter and throws on unknown calls and on any filter a branch does not evaluate (`bareFiltre`), so a new column in the subscriber select, a new query or a new filter must be added to the fake — the error names what is missing. The account-less signup (`/api/soppvarsel/pamelding`, also the `VarselCta` form on the area pages, which no test may ever submit) has a throttle **per inbox** in three layers (`src/lib/alerts/pameldingstak.ts` plus an in-memory limiter slot that is refunded unless a confirmation actually went out), and every layer answers «sendt», never 429, so the route is not an oracle for which addresses are signed up — the status text must stay true when nothing is sent. Per inbox, not per string: +tags and Gmail's dots (and googlemail.com) reach the same inbox, so counting the literal address let a script send three confirmations an hour per spelling. Layer 1 hashes `kanoniskAdresse` (lower-case, +tag stripped, Gmail dots removed, googlemail.com folded into gmail.com); layer 3 counts with `regexIMatch('email', adresseMonster(...))`, an anchored, fully escaped pattern that matches exactly the stored spellings of that inbox — never `ilike`, where a prefix match would let anyone fill a stranger's cap and have their confirmations swallowed behind «sendt»; layer 2 stays an exact `eq`. Rows store, and the mail goes to, the typed address lower-cased; only a bare addr-spec of at most 254 characters is accepted («ugyldig» otherwise), because display-name, comment and list forms made the counted string differ from the one the mail was delivered to. `sendEpost` has a 15 s limit (`RESEND_FRIST_MS`) and never throws, and the limit must stay generous, because a slow but successful send counted as failed would make the alert cron send the same flip again the next day. A failed confirmation is retried once after `NYTT_FORSOK_ETTER_MS` (1 s) with the same Resend idempotency key, `soppvarsel-bekreft/<row id>/<sha256(token) prefix>` (a rotated token gets a new key): a timeout may have sent the mail, so only a second failure rolls the row back. The route's `maxDuration` (60) must cover both sends and the pause (2 × `RESEND_FRIST_MS` + `NYTT_FORSOK_ETTER_MS`), or a killed function leaves an unconfirmed row that layer 2 answers «sendt» without sending. The e-mail placeholder in both signup forms is `COPY[locale].epostEksempel` (`src/app/soppvarsel/tekst.ts`) and stays on example.com (RFC 2606) — a «translated» example domain can belong to someone. The `/soppvarsel` area select starts on a visible, disabled prompt (`COPY.velgOmrade`) that must stay its first child, outside any `optgroup`, or `required` stops blocking an empty submit.

**Security headers + CSP** (`next.config.js`). Six baseline headers on every response: HSTS, X-Frame-Options: DENY (matches CSP `frame-ancestors 'none'`), X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy (camera + geolocation for self), X-XSS-Protection: 0. Plus an **enforcing** `Content-Security-Policy` (flipped from report-only in June 2026) with allowlists for Stripe, Supabase, Wikimedia, Kindwise, Kartverket, OSM, GA4. A new third-party host MUST be added to the allowlist before deploy — otherwise the browser blocks it silently (no report-only safety net any more). `images.remotePatterns` is derived from `NEXT_PUBLIC_SUPABASE_URL` when the config loads — our own host, `/storage/v1/**` only, and an empty list if the variable is missing or invalid. It allowed `**.supabase.co` and `**.kindwise.com`, so any Supabase project in the world could be resized on our bill. No component uses `next/image` (species photos are plain `<img>`), so the list only bounds what the optimiser can be used to proxy; `src/lib/__tests__/next-config-bildeverter.test.ts` guards it.

**GDPR endpoints.**
- `/api/me/export` (Art. 15): authenticated GET; returns a JSON file (Content-Disposition: attachment) with every row tied to the user's id across `profiles`, `findings`, `forum_posts`, `comments`, `post_likes`, `comment_likes`, `saved_posts`, `reports` filed, `billing_subscriptions`, `moderator_roles`, `verified_foragers`, `spot_feedback`, `account_deletion_warnings`, `ai_identifications`, `identifications`, `alert_subscriptions` (by user_id **and** by e-mail, so account-less signups are included; tokens stripped) and `blocked_users`, plus `user_metadata` (kilde, terms consent) under `account`. Multi-row datasets are paginated (PostgREST caps at 1000 rows silently — a truncated export would otherwise be labelled complete). Most datasets are read with the session client (RLS is the source of truth). The exceptions are read with the admin client, filtered explicitly on the caller's id/e-mail, and each exists because the session client would silently return *less than we hold* in a file that calls itself complete: `ai_identifications` (and `prove_paaminnelser`/`prove_svar`) have RLS with no policies; account-less alert rows have no user_id; and `forum_posts` and `comments` have a SELECT policy that requires `is_hidden = false` even for the author, so a post or comment a moderator has hidden — still stored, still personal data — dropped out of the export (`is_hidden` is in the row, so the user can see what was hidden). `verified_foragers` is also read with the admin client (own row only): migration 074 withdraws the moderators' internal `note` column from the anon/authenticated roles, and the note is personal data about the user, so it stays in the export. 074 belongs to the release this code shipped in: it is pasted the same day, *after* the deploy (before it, the old export code answers 500 for everyone) — the five steps are at the top of `docs/migrasjoner-a-kjore.md`, and until its row there says «kjørt» the job is half done. Excludes reports filed by *others* about the user (would expose reporter) and `admin_audit_log` rows mentioning the user (they identify the acting administrator too).
- `/api/me/delete` (Art. 17): authenticated POST with literal `{"confirm":"DELETE-MY-ACCOUNT"}` body. Hard-deletes the auth.users row via the admin client; FK cascades wipe profile and dependent rows. Returns receipt with deleted-row counts (still read with `count ?? 0`, so a count that failed reads as «0 deleted» — the class described under Health check). Before the Stripe cancellation (the one step that cannot be undone, so it stays last before the account delete) it also deletes the account-less alert sign-ups on the account's own address (`alert_subscriptions` with `user_id IS NULL` and an exact lower-cased e-mail match — nothing cascades to them, and they kept mailing a person whose account was gone); the receipt counts them as `counts.emailAlertSubscriptions`. `supabase/functions/purge-inactive-accounts` does not do this yet. Error bodies are `{ error, code, details }` via `apiFeil`, with `details` the localized «retrying is safe» text.
- `/personvern` page: complete privacy policy in **both nb and sv** — no `[FYLL INN]` placeholders remain (verified: `src/lib/legal/__tests__/entity.test.ts` asserts the rendered legal text contains none). Real controller + org number, all four Art. 6 bases, nine named processors with DPA links, concrete retention periods, and the right supervisory authority per language (Datatilsynet on nb, IMY on sv). Still needs a **lawyer review** before launch — that is the only outstanding item, not filling anything in.

**Paying, trials and gift passes (daily report and /admin).** One rule — `klassifiserAbonnement` in `src/lib/rapport/abonnement.ts` — feeds both the daily report and the `/admin` statistics page; each row lands in exactly one of `betalende` / `prove` / `gratisTildelt` / `utlopt` / `inaktiv`. «Betalende» is a store row (Stripe or App Store) with status `active` and a running period, whatever its tier (see below). `trialing` is *not* «betalende» and has its own block (løpende, startet 7 d, til første belastning, avbrutt). **App Store trial reminder** (`prove_paaminnelser` + `prove_svar`, migration 072; cron `/api/cron/prove-paaminnelse-app` 06:30 UTC daily). Apple sends nothing before an intro offer converts, so unlike the web (Stripe's `trial_will_end` → the webhook's e-mail) the day is computed here: RevenueCat-owned `trialing` rows that are not `SANDBOX` and not `cancel_at_period_end` get `byggAppProvePaaminnelseEpost` when `current_period_end` (as Oslo date) is 3 days ahead, or 2 as a catch-up, never 1 or 0 (`bestemAppProvePaaminnelse` in `src/lib/billing/prove-paaminnelse-app.ts`). The sent marker lives in its own table keyed by `(user_id, kanal, prove_slutt)` because both webhooks rebuild `metadata` on every write; the cron **reserves the row before sending** (a `23505` on insert means another run took it → skip) and deletes it when the send fails, so a failed send retries next morning, at most once more inside the window — marking *after* the send was not safe, because Resend's idempotency key lives 24 h and the cron runs every 24 h. A missing table means warn-and-skip, never send. Three honesty rules in the copy: it never states an amount (the RevenueCat webhook stores no price or currency, and the App Store price is set per country by Apple, so it says «prisen som sto i appen da du startet» and must never take a number from `plans.ts`); the cancel deadline is `current_period_end − 24 h` as an Oslo day and floored hour («senest 26. september kl. 07», «senest i morgen kl. 07» on the catch-up day) because Apple attempts the renewal within the last 24 h, and the path is Apple's real one — «Innstillinger → navnet ditt øverst → Abonnementer» plus `APPLE_ABONNEMENT_URL`, never «Apple-ID», which is no longer a row or a name; and «gratisuka»/«gratisvecka» is used only when `current_period_start → current_period_end` is 6–8 days (`erGratisuke`), otherwise the web wording «prøveperioden» verbatim, since offer codes can be 3 days or a month. The one-tap question at the end links to `GET /api/prove/svar?t=…&valg=…` with an HMAC token over user id, trial end **and send time**, derived from `SUPABASE_SERVICE_ROLE_KEY` (`src/lib/billing/prove-svar-token.ts`); the route writes on GET only for a real navigation (`Sec-Fetch-Dest: document` + `Sec-Fetch-Mode: navigate`) at least `AKTIVERING_MIN_MS` after the send, otherwise it shows the same page with one button and writes on the `POST` — mail-link scanners fetch all three links within seconds and would otherwise record «ai» for people who never opened the mail. Answers land in `prove_svar` and appear in the daily report as «Svar fra prøvestartere (7 d)». Both tables are personal data: `/api/me/export` carries them as `trialReminders` and `trialAnswers` (admin client, schema 7) and `/personvern` names them under betalingsdata.

**Rapportpuls** (`rapportpuls`, migration 069; retired 17 Sep 2026 — the 04:40 UTC cron is gone from `vercel.json`, and the route `/api/cron/rapportpuls`, `src/lib/rapportpuls/` and the optional `puls` argument of the alert e-mail and the X flip post were deleted in Nov 2026, so nothing can write or print it; only the table and migration 069 remain as history). It compared, per region, GBIF fungi records in the window `[day−13, day−7]` with the mean of the same window in 2023–25. **Not shown to customers since 17 Sep 2026** — the alert e-mail and the X flip post no longer receive it. The original lag reasoning was wrong: the gap is not GBIF ingestion but people entering finds into Artsobservasjoner weeks to months after the trip (by mid-September only 57–74 % of a year's August records exist; ~95 % by New Year). Comparing an unfinished current window with finished prior years therefore reads «under» almost everywhere every autumn (Kristiansand −92 % went out in two alert e-mails on 15–16 Sep), and the small region boxes are dominated by single recorders (Stavanger +555 % on a baseline of 20). A fair comparison counts prior years *as they stood on the same date*, using Artsobservasjoner's sighting id (GBIF `catalogNumber`, dataset `b124e1e0-4755-430f-9eab-894f25a9b59c`), which rises in entry order. Never re-expose a year-over-year number outside the owner's report without that same-date baseline.

**Soppregistreringer, same date as before** (`soppregistreringer`, migration 071; cron `/api/cron/soppregistreringer` 05:45 UTC daily). Answers «is there less mushroom this year, and where?» for the owner's daily report without the entry-lag lie: people enter finds into Artsobservasjoner weeks to months after the trip (mid-September holds only 57–74 % of a year's August records, ~95 % by 1 January), so raw 2026 vs finished 2023–25 always reads as a slump. Artsobservasjoner's sighting id (GBIF `catalogNumber`) rises in *entry* order, so prior years are counted **as they stood on the same date**: for year Y the cutoff is the highest id among the dataset's records with `modified` = Y-MM-DD, where MM-DD is the current GBIF snapshot (dataset `pubDate`); 2023–25 count only ids ≤ cutoff, this year counts everything, normal = mean of the three. Windows «sesongen hittil» (1 Aug → snapshot − 7 d) and «siste hele uke» (the 7 days ending there), Norway + the 15 counties of 2024 built from GBIF's GADM 3.6 facet (never `stateProvince`), groups `alle` (taxonKey 5) and `storsopp` (Agaricales/Boletales/Russulales/Cantharellales). Pure logic in `src/lib/rapport/soppregistreringer.ts`; fetching in `soppregistreringer-henting.ts` — 64 GBIF calls because county × group × window come from intersecting id sets instead of separate calls, 2 s between calls (faster gives 429), ~150–210 s, 270 s deadline; every catalogNumber facet (counts *and* cutoffs) stops the run when it hits `facetLimit` or covers < 99 % of `count`, because a truncated facet drops the highest ids and looks fine. **`/process` saying `FINISHED` means nothing for the index:** it describes the download, finishes a minute after the crawl starts, and its newest entry is often a `NOT_MODIFIED` no-op (12 Sep edition: crawl 11:28, `pubDate` 11:35, no-op `FINISHED` 11:36, search index 13:22). `sjekkIndeksering` therefore fails closed unless the newest `NORMAL` crawl attempt has a `/pipelines/history` entry, no `INTERPRETED_TO_INDEX` of that attempt is running, and the crawl's own `INTERPRETED_TO_INDEX` is `COMPLETED` *after* the dataset's `modified`. The weekly crawl runs Sundays ~03:00–03:35 UTC and indexing finishes ~05:00–05:20, hence 05:45 (before the 06:00 report); a night the gate says no costs nothing, a wrong snapshot would stand for a week. If the count runs out or GBIF fails twice nothing is written and the next night redoes the whole snapshot (one upsert of 64 rows; a row for the snapshot means done). `tynt` (*) = normal < 50 or the three years differ by more than 3× (a few recorders). Dry run against live GBIF, no DB: `npm run torrkjor:soppregistreringer -- --til=2026-09-07` (verified 17 Sep 2026: Norway 92 %, storsopp 86 %, all 15 counties within ±5 points of an independent count). These are **recording activity, not mushroom quantity** — shown only in the owner's report with its fixed caveat, never to customers, never in alerts or X posts. The block replaced the rapportpuls line in the daily report; with the alert e-mail and X posts no longer reading `rapportpuls` either, its 04:40 cron, route and lib were removed and the table is history. The same report row «Nye kontoer (14 d) som følger et område» links account-less alert rows to accounts by lower-cased e-mail in memory only; no address reaches the report, log or JSON.

**AI-identifiseringen is monitored, because it died silently once.** Kindwise takes `details` and `language` as **query params**; in the body it answers 400 «Unknown modifier», and from May to 29 Sep 2026 every call did exactly that while the user saw «Identifikasjon feilet» — `ai_identifications` (migration 020) got a row only for a call that succeeded, Sentry drops kindwise.com on purpose, so «nobody uses it» and «it is dead» were the same zero for four months with 2 050 credits untouched. Three things now make that visible: `kindwise-request-shape.test.ts` locks the request form; every failed Kindwise call writes one row (a status code only, no user id) to `ai_identifiseringsfeil` (migration 073, purged after 30 days) — the HTTP status Kindwise answered with (the response body goes to the log), or **status 0 when no answer ever came** (timeout, DNS, a reset connection, a body that stops half-way); and `src/lib/identifications/kindwise-status.ts` reads Kindwise's `usage_info` (costs no credits) for `/api/health` (`checks.ai`, a coarse state only — see Health check) and for the daily report's «AI-identifisering» block, the only place the numbers appear, which raises `ai.varsel` when calls fail without any succeeding, when Kindwise blocks the key, or when credits drop under `KINDWISE_KREDITT_VARSEL`. `scripts/sjekk-kindwise.mjs` sends the route's exact request from a laptop when the app says «Identifikasjon feilet». The status-0 row closed the same blind spot for a different failure: a `fetch` that threw went straight to the route's outer catch and was counted nowhere, so a Kindwise that hung was as invisible in the report as the four months of 400s had been.

**The free AI quota is reserved before the paid call, and every wait has a deadline.** `/api/identify` used to count the day's calls, wait seconds on Kindwise and write the `ai_identifications` row afterwards — so every request that arrived while the earlier ones were still at Kindwise saw the same number, and a free account on 4 of 5 could fire as many parallel calls as the 20/min burst limiter let through. A free account now inserts its row *first* and counts the rows in the 24 h window with id ≤ its own; over the cap, the row is deleted and the answer is `daily_quota`. The reservation is **released when the call cost nothing** (Kindwise rejected it, or never answered) and stands once Kindwise has answered OK, whatever happens afterwards — the credit is spent. Paid and trial accounts have no daily cap (the plan is sold as «ubegrenset»; a ceiling is prepared, but the number is the owner's decision and needs the price page and the terms changed in the same PR) and get their row after an OK. The day's count goes through `tellRader`, never `count ?? 0`: a missing `ai_identifications` table falls back to the saved-find count, and «no number» from either count stops the call with 500 instead of reading as 0 used. A row therefore still means «a credit was spent», which is what the daily report counts; the known leftover is a function killed between reservation and release (`identify.reservation_release_failed` when the delete itself fails). Deadlines: `KINDWISE_TIMEOUT_MS` (25 s, each call its own signal, also covering the body read) under the route's `maxDuration` of 60 → `provider_timeout` (504), with no automatic retry, which could cost a second credit for the same photo. The client (`src/lib/hooks/useIdentify.ts`) sends with XHR so its deadline can follow upload *progress* (`IDENTIFY_STILLSTAND_MS` without a byte moving, `IDENTIFY_SVARFRIST_MS` for the answer): a flat 75 s cap cut every attempt on a slow forest uplink, or threw away an answer the server had already paid for. It tells `upload_stalled` (nothing was spent — retry) from `timeout`/`response_lost` (the server may have done the whole job — point to the history, never invite a blind retry).

**An AI suggestion never gets a green «spiselig» stamp.** `<AiEdibilityBadge>` (`src/components/identify/AiEdibilityBadge.tsx`) keeps the toxic, deadly, inedible and unknown badges and replaces the two edible classes with a neutral «ikke matvurdert»: a warning is useful even when the species ID is wrong, a green stamp is harmful exactly then. The rule lived only in the result view; the look-alike card and the history list used a raw `<EdibilityBadge>` and stamped the same suggestion green. Use the component wherever a suggested species is shown — `edibility-asymmetry.test.ts` reads every source. The same asymmetry decides which look-alikes the result may call dangerous (`visesSomFarligForveksling` in `src/lib/identifications/enrich.ts`): `look_alikes` is directed and some pairs exist in both directions, and the row written from the dangerous side points at the *edible* species — a deadly suggestion got «Farlig dobbeltgjenger: Sjampinjong» with a green «Spiselig» (4 of the 28 high/critical rows in production on 16 Nov 2026 were such mirror rows). So a row whose look-alike is food (`isRecommendableSpecies`) is dropped when the suggestion's catalogue edibility is not food; rows whose look-alike is toxic, deadly, inedible or unknown always stay; a non-food suggestion left without rows still gets `lookAlikeData: 'none_recorded'`, but the result card shows the «ikke ført inn ennå» note only under a food suggestion (`isRecommendableSpecies`) — under the four mirror species (two of them deadly) it claimed no look-alikes were entered while their species page listed the pair, and there the suggestion's own Uspiselig/Giftig/Dødelig/Ukjent badge is the warning. The card's red look-alike line follows the same class: «sjekk nøye før du spiser» only under food, `lookAlikeWarningNotFood` («— ikke spis den») under the rest — under Svovelsopp (toxic) and Honningsopp (inedible since 047), whose rows to each other stay, «før du spiser» read as edible-if-careful — and it speaks only of the suggestion, because a result stored in the session before the mirror rule can still list a food twin. `LookAlikeCheck` shows the raw `EdibilityBadge` only on a twin that is not food. (The species page still shows pairs from both sides, with their direction.) The suggestion's season pill follows the calendar's rule (`SeasonNow`, `YearTable`): for `isDangerousEdibility` it is neutral grey and never says «Topp-sesong». Poison-centre numbers come from the `Safety` namespace through `byggGiftnummer` (Sweden has two, Norway one) and are never hardcoded at the call site.

**Health check** (`/api/health`): public, no auth. `?fast=1` skips DB checks for high-frequency probes. Returns 200 with per-check `{ok, message}` pairs covering env vars, database, audit log table presence; 503 if an uptime check (env vars, database, audit log table) fails; `checks.epost`, `checks.ai` and `checks.tabeller` are reported but never cause a 503. Wired into the logger at debug/warn levels. `checks.ai` (non-fast only, cached 5 min; the key is never set locally) is coarse on purpose, because the route is public: `{ ok, tilstand, message }` with `tilstand` one of `ok | lav | sperret | utilgjengelig | mangler-nokkel` (`kindwiseTilstand`), no credit count and no Kindwise response text. `lav` (under `KINDWISE_KREDITT_VARSEL`, shared with the daily report) still counts as ok; the details go to the log as `health.ai_detalj`. `checks.tabeller` (non-fast only, cached 5 min) lists tables from newer migrations that are missing (`NYERE_TABELLER` in `src/lib/supabase/tabell-finnes.ts`). **Gotcha:** a missing table arrives from PostgREST as `PGRST205`, not Postgres' `42P01`, and a HEAD count (`select(..., {count:'exact', head:true})`) against a missing table comes back as `error = null, count = null` — so `count ?? 0` turns a forgotten migration into a silent zero. Use `erManglendeTabell` / `tellRader` from that file instead of testing for `42P01`.

**Toaster** (`react-hot-toast`) is mounted in `src/components/layout/Providers.tsx` — `toast.success` / `toast.error` work app-wide.

**Every modal dialog and sheet uses `useDialogFokus`** (`src/components/ui/useDialogFokus.ts`). Each sheet was a hand-written `<div role="dialog">` where Escape did nothing, focus stayed on the button behind the backdrop, Tab wandered on into the page underneath (also under «Slett kontoen») and focus was gone after closing. The hook does four things while `aapen` is true: moves focus to the **panel** (`tabIndex={-1}`), not the first field — a focused input pulls up the iOS keyboard, and in the delete dialog the first stop would be a destructive control; closes on Escape, but only the topmost dialog and only when `kanLukkes` (the trial sheet can lie on top of the intro); keeps Tab inside the panel; and returns focus on close (never to a text field, for the keyboard's sake). Deliberately no `inert` or `aria-hidden` on the rest of the page — `aria-modal` covers screen readers, and `inert` would take the toaster, stacked sheets and the intro's promise that a scrim can never lock the app. Close buttons use `LUKKEKNAPP_KLASSER` (a 44 × 44 px target around the icon). A new modal without the hook is a regression; the hook's test file shows the expected behaviour. The one `role="dialog"` that must **not** get it is the cookie notice (`src/components/layout/CookieNotice.tsx`): it is not modal — no `aria-modal`, no scrim, a card above the bottom nav — and the app has to stay usable until it is answered. **i18n** (`src/i18n/`, next-intl, no URL prefixes). Locale comes from the `MYCELET_LOCALE` cookie, falling back to `Accept-Language` and then `nb`. Client components use `useTranslations()` / `useLocale()` against `messages/{nb,sv}.json`; server code calls `getUserLocale()` from `src/i18n/locale.ts`.

`/soppforhold` (the app's logged-out first screen) follows the visitor's locale: copy from the `Soppforhold` namespace, verdicts and species names via `hentRegioner(locale)`, and **Sweden's section first for `sv`** (`regionerPerLand`). The area pages `/soppforhold/[omrade]` instead follow the region's *country* (Göteborg is always Swedish, with Swedish poison-centre numbers), so each shared URL has one language for crawlers. Gotchas that produced real Swedish-user bugs:

- **Text generated server-side is not covered by next-intl.** Anything an API route returns as prose — prediction verdicts, flush banners, habitat reasons, weekday labels, "nothing found" messages — needs the locale threaded in explicitly. The pure prediction libs (`src/lib/prediction/mushroom-day.ts`, `flush.ts`, `src/lib/utils/prediction-explanation.ts`, `src/lib/nibio/habitat.ts`) each take an optional `locale` and hold a per-language `COPY` table next to the logic; they default to `nb` so tests and pre-generated tiles are unaffected. **If a route caches its response, the locale must be part of the cache key** — otherwise the first caller's language is served to everyone.
- **Species names come from the database, not the message catalog.** Use `getSpeciesDisplayName(species, locale)` from `src/lib/utils/species-name.ts` and select `swedish_name` alongside `norwegian_name`. It falls back to Norwegian silently, so a missing `swedish_name` shows as Norwegian text rather than an error — verify new species rows have both. Source Swedish names from SLU Artdatabanken (artfakta.se / Dyntaxa, which GBIF exposes with a `preferred` flag), never by translating the Norwegian name: several Swedish mushroom names differ by only a word from a *different* species' name. The database *prose* is Norwegian only (`description`, `edibility_notes`, `toxin_info`, `symptoms`, the look-alike similarity/difference texts): Swedish readers get it marked `lang="nb"` with one Swedish note line (`SpeciesDetail.norwegianProseNote` / `norwegianLookAlikeNote`, `LookAlikeCheck.norwegianTextNote`), and safety text is never hidden. Remove those notes if Swedish prose columns are ever added.
- **Swedish that is Norwegian in disguise.** Swedish copy is often written from the Norwegian, and some words look the same without meaning the same. Norwegian «lite» means «not much»; Swedish «lite» means «a little, some», so «Lite svamp här nu» on the lowest rung read as cautious good news — write «ont om» / «inte mycket», and never use a bare «lite» as a negative («För lite fukt», «det har bara kommit lite nederbörd» are fine). A map does not «stå» in Swedish («mitt på kartan», «kartans mittpunkt»); «vad som står där» reads as «what is written there» (mushrooms «växer»); «bäst till ligger» does not survive the Norwegian word order («bäst är det kring …»). `src/lib/__tests__/svensk-ordvalg.test.ts` guards the message catalog against every pair found so far — add new ones there; it does not read the server `COPY` tables (`src/lib/prediction/*`, `prediction-explanation.ts`), so check those by hand.

**Dates are formatted in the reader's zone, and «days ago» are calendar days.** Server components, routes and the helpers they call run on a UTC server, so `toLocaleDateString` / `Intl.DateTimeFormat` there must get `timeZone: timeZoneForLocale(locale)` (`src/i18n/config.ts`) — done on `/mine-steder`, `/identifiseringer`, `/profile` (also «medlem siden» in `src/lib/utils/member-since.ts`) and the home page's community list; a find from 00:30 Norwegian time otherwise got yesterday's date, and an account created at 00:30 on 1 December was «medlem siden november». Relative labels («i dag», «i går», «for N dager siden») count Oslo calendar days, never elapsed hours divided by 24 (`formatTimeAgo` in `src/lib/utils/time-ago.ts`, `osloIDag` + `dagerMellom`): a find from 23:30 yesterday was «i dag» at 08:00. Tests for this set `process.env.TZ = 'UTC'` at the top of the file (see «Localized API errors»).

Pre-generated `prediction_tiles` store habitat reasons in **both** languages since PR #118 (`reasons` + `reasonsSv` in tile metadata), and the tile path of `/api/prediction` picks by locale — so every path is localized. Tiles older than 2026-08-02 lacked `reasonsSv`, but the raster regenerates nightly, so that gap closed itself.

## Database notes

PostGIS is required (extension created in 001). Geo queries on `findings` and `prediction_tiles` use GIST indexes on `ST_SetSRID(ST_MakePoint(lng, lat), 4326)`.

**Trigger functions that write elsewhere must be `SECURITY DEFINER` with a locked `search_path`** (`set search_path = public, pg_temp`, table names qualified). A plain (`SECURITY INVOKER`) trigger function runs as whoever fired it: under RLS its write hits 0 rows with no error, and in an `auth.users` cascade it would run as Supabase's auth role. That is how `forum_posts.comments_count` and `likes_count` (triggers from 001 on `comments` and `post_likes`) counted only the post author's own comments and likes until migration 076 — the only UPDATE policy on `forum_posts` is owner-only, so an answered question stayed under «Ubesvarte» (which looks for `comments_count = 0`) and someone else's like jumped back on the next fetch. 076 makes both functions definers, keeps the comment counter following `is_hidden` as 041 does (insert, delete, and an UPDATE that flips it), moves the count along when an UPDATE changes a comment's `post_id`, and recounts every post; `src/lib/forum/__tests__/tellere-migrasjon.test.ts` reads the file. A definer counter has to hold for everything a user may do to their own row: the comments UPDATE policy only checks `auth.uid() = user_id`, so an author can move their own comment to another post, and a counter that looked only at `is_hidden` would have let anyone zero another post's count (move a comment there and delete it) or inflate it the other way — as invoker that write hit 0 rows, so it was the definer change that opened the door. 076 also narrows UPDATE on comments for `authenticated` to `content`, all the app edits, but only as a second layer: the restore block below reopens every column, so the move branch is the guard. Every counter change also bumps `forum_posts.updated_at` (trigger `forum_posts_updated_at` from 001), so never read `updated_at` on posts as «edited».

If anyone runs `DROP SCHEMA public CASCADE` to reset the database, Supabase's automatic table grants for `anon` and `authenticated` are wiped. Symptom: REST/browser queries fail with `42501 permission denied for table X` even though RLS policies look correct. Restore with:

```sql
GRANT USAGE ON SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL TABLES IN SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL FUNCTIONS IN SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO anon, authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO anon, authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON FUNCTIONS TO anon, authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON SEQUENCES TO anon, authenticated, service_role;
```

## Framework quirks worth knowing

Most of these came up during the Next 14 → 16 upgrade; the last two are Capacitor's:

- **`cookies()` is async.** Returns `Promise<ReadonlyRequestCookies>`. Either `await` it or capture the promise once at construction and `await` inside callbacks (the pattern in `src/lib/supabase/server.ts`).
- **`ssr: false` on `next/dynamic` is disallowed in Server Components.** Wrap the dynamic import in a thin `'use client'` component (see `src/components/map/MushroomMapLazy.tsx`).
- **`useSearchParams()` requires Suspense for prerendering.** Wrap pages that use it in `<Suspense>` with a fallback. Pattern: extract the hook-using body to an inner component, wrap from the default export. Already done for `/auth/login`, `/auth/register`, `/forum/new`, `/pricing`.
- **Middleware-set response headers don't propagate when a route handler builds the response.** The init-headers form `NextResponse.next({headers})` and the post-construction `response.headers.set()` both fail to reach the client. The request-header rewrite half DOES work (so `createRequestLogger` picks up `x-request-id` correctly server-side). See `docs/logging.md`.
- **`loading.tsx` makes the route stream, and a streamed response cannot change its status.** `/map`, `/mine-steder`, `/profile` and `/identifiseringer` have one (skeletons in `src/components/ui/SideSkjelett.tsx`) so a tab tap shows the shell at once — in the app on one bar of coverage, the previous screen used to stand untouched until the whole answer had arrived, and the tap looked dead. The price: once the skeleton is on its way, `redirect()` and `notFound()` can no longer set the HTTP status; the redirect becomes a 200 plus a client-side redirect (see the QA gotcha above). So never add a `loading.tsx` at the root of `src/app`, or under `species/` or `soppforhold/` — an unknown species or area would answer 200 instead of 404. The home page streams the other way: `src/app/page.tsx` decides logged-in/out before anything streams (logged-out visitors get `LandingPage` whole), and the logged-in content is one async component inside a `<Suspense fallback={<HjemSkjelett />}>` in the page, with every per-user query in one `Promise.all`. `ProvGratisVedStart` must stay *before* `MushroomDayCard` in that same boundary, because the card announces `FORSIDEKORT_KLAR_EVENT` once per mount — right after mount on a cache hit — and a sheet rendered later would miss it. Skeletons carry no text (nothing to translate) and no `<RegistrerBruksdag>` (a page that was never shown must not count as a usage day).
- **Prerender + Supabase env vars.** Pages that call `createClient()` need env vars at build time. Either keep `.env.local` populated locally during build, or mark such pages `force-dynamic` if they must run without env at build time.
- **Never run `npx cap sync` from a git worktree.** It rewrites the relative paths in `ios/App/CapApp-SPM/Package.swift` to match the worktree's depth (`../../../../../../node_modules` instead of `../../../node_modules`). The file is tracked, so committing that breaks the iOS build for everyone in the main checkout. `Info.plist` is safe — sync leaves it byte-identical (only `cap add` rewrites it, via `editProjectSettingsIOS`) — but if you do run sync in a worktree, `git checkout -- ios/App/CapApp-SPM/Package.swift` afterwards.
- **Never let a Capacitor plugin pass through a promise.** A plugin object is a Proxy that answers *every* property name, `then` included. Resolve a promise with it — `import('@capacitor/geolocation').then((m) => m.Geolocation)`, or `return Geolocation` from an async function — and the promise machinery takes it for a thenable and calls the native method `then`, which does not exist: «"Geolocation.then()" is not implemented on ios» as an unhandled rejection, and a promise that never settles. That hung every position lookup in the iOS app from the #284 deploy on 17 Oct 2026 until the hotfix (#285) — «Identifiser» stood on «Henter posisjon …» — and it was the second time (`loadPlugin` in `src/lib/native/purchases.ts` documents the first). Cache the *module* and destructure the plugin after the `await` (a module object has no `then`), or wrap the plugin in a plain object, as those two files do. The tests passed because their fake plugin was a plain object: a fake plugin must be a Proxy that rejects every unknown method, `then` included (`src/lib/hooks/__tests__/useGeolocation-native.test.ts`).

## Conventions

- UI text in Norwegian; new strings should match tone of existing copy in `src/app/`. Don't translate user-facing copy to English.
- Zustand stores live in `src/store/`. TanStack Query for server-state caching is preferred over manual `useEffect` fetches.
- Tests live next to source in `__tests__/` folders. Pure utility functions (`src/lib/billing/plans.ts`, `src/lib/utils/prediction.ts`, `src/lib/utils/species-scoring.ts`, `src/lib/log/*`, `src/lib/rate-limit/*`, `src/lib/weather/*`) all have tests — keep that going. UI components are largely untested.
- The repository is **public**, so a recipe says *where* a secret is kept, never what it is. Three real ones — two account passwords and the company's IBAN — were pasted into `docs/` «just for now» and are still in the git history. `src/lib/__tests__/docs-uten-hemmeligheter.test.ts` is that rule as a test, over every text file git would commit (`git ls-files --cached --others --exclude-standard` in `src/lib/__tests__/repo-filer.ts`, so the suite needs a git checkout — CI's `actions/checkout` provides one; a fixed list of directories had missed the root files, most of `public/`, `ios/`, `android/` and `.github/`): no password, IBAN or «user / password» pair in any `.md`, this file included; no secret as a string constant outside `src/` and `messages/` (read it from the environment); keys, secrets, tokens and `AUTH`/`CLIENT_ID` names in `.env*` files empty or placeholders; and no address at a private mail provider in any file, test fixtures and comments included — build one from parts (`[lokal, 'gmail.com'].join('@')`) and use `example.com` or `.example` everywhere else.
- `.env.example` lists every variable the app reads, and `src/lib/__tests__/env-eksempel.test.ts` keeps it so. It lacked `CRON_SECRET`, `RESEND_*`, `REVENUECAT_*`, `X_*`, `MET_FROST_CLIENT_ID` and `PRESSE_VARSEL_TIL`, so a setup from it got 401 from every cron route and never our own password-reset mail, with nothing saying why. A new `process.env` read in `src/` or `next.config.js`, or a credential-like name in `scripts/`, needs a line with a placeholder and a one-line comment — an empty value when the code checks truthiness, a commented-out line when it reads the name with `??` (an empty string would override the default) — and a name no code reads must go. Never put the analysis scripts' run options or `QA_TEST_*` there: the scripts run with `--env-file=.env.local`, where a copied empty line replaces their defaults, and `npm run qa:setup` writes `QA_TEST_*` into `.env.local` only when the name is missing.
- Species names in narrow cards (library, calendar rows, look-alike trainer) go through `<Artsnavn>` (`src/components/species/Artsnavn.tsx`): one inline block per word with `break-words` + `hyphens-auto`, because «Snøballsjampinjong» was cut off by the card edge on a phone. Never put `hyphens-auto` on a whole multi-word name — Safari, and so the app's WKWebView, then hyphenates words that could simply move to the next line — and never `truncate` a species name.
- iOS zooms the whole page when a field under 16 px gets focus and does not zoom back out, so a global rule in `src/app/globals.css` (`@supports (-webkit-touch-callout: none)`) forces 16 px on inputs there. Do not fight it per component, and never «fix» the zoom with `maximum-scale=1` or `user-scalable=no` — that turns off pinch zoom for everyone. «Reduce Motion» is honoured by a global rule in the same file (Leaflet is exempt: it waits for `transitionend`); scrolling from code must ask `rulleAtferd()` (`src/lib/utils/bevegelse.ts`), because CSS cannot override an explicit `behavior: 'smooth'`.
- Commit message style: short imperative subject in English (matches `Step N: ...` history). Co-author the AI helper with `Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>`.
- The README and most planning docs are in Norwegian. `docs/strategi-2026-2027.md` is the current human-facing source of truth for priorities and what's left to build (`docs/roadmap.md` is history and says so itself); `docs/logging.md`, `docs/8-step-status.md`, `docs/commercial-mvp-plan.md`, and `docs/offline-map-mvp.md` are good orientation reads for understanding intended scope.
