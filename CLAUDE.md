# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mycelet (rebranded from SoppJakt 2026-05-09) — a Norwegian (and Swedish) mushroom-foraging app. UI strings, docs, and commit messages are in Norwegian. Code identifiers and CLAUDE-facing notes are in English.

Stack: Next.js 16 (App Router, Turbopack) + React 19 + TypeScript + Tailwind + Supabase (PostGIS) + Stripe + Leaflet 5. State via Zustand and TanStack Query. Tests via Vitest.

## Common commands

```
npm run dev         # Next dev server on http://localhost:3000
npm run build       # production build (Turbopack; runs tsc as part of build)
npm run typecheck   # tsc --noEmit
npm run lint        # next lint
npm run test        # vitest (runs all tests)
npm run test -- src/lib/weather    # filter by path

npm run qa          # full product evaluation (Playwright) vs local dev — the main QA loop
npm run qa:prod     # read-only smoke + gating vs live mycelet.com (safe against prod)
npm run qa:setup    # create the dedicated QA test user (run once)
npm run qa:report   # open the last Playwright HTML report
```

Tests use the `@/*` path alias from `tsconfig.json`; vitest mirrors this in `vitest.config.ts`. Add new tests next to source in `__tests__/` folders — they pick the alias up automatically.

There is no Supabase CLI workflow set up; migrations are applied by pasting `supabase/migrations/NNN_*.sql` into the Supabase SQL Editor in number order (001 → 074 at the time of writing). Which of them are actually applied in production is tracked per migration in `docs/migrasjoner-a-kjore.md` — **the statuses there for 039 onward are unconfirmed until the owner has checked them against the database; do not assume a migration is applied (or not) from this file.** A PR that adds a migration adds its row to that ledger — to the table and to the single read-only query there that answers for every migration from 039 (`src/lib/__tests__/migrasjonshovedbok.test.ts` fails if either is missing). Only paste a file whose row reads `false`: the ledger lists where an early migration pasted after a later one bites (041 after 056, 043 after 054, 049 after 065, 066/067 after 068). They have hard dependencies — running 003 alone fails because it references `mushroom_species` and `update_updated_at()` from 001. Migration 008 (audit log) requires `moderator_roles` from 002.

## QA automation & standing habits

**Full product evaluation loop** — Mycelet's main QA automation. `npm run qa` drives every core flow (map + NO/SE geo-routing, AI identify, prediction, calendar, forum, auth + forgot-password, billing web/native gating, species, /datakilder, /api/health) against the success criteria in `docs/qa-sjekkliste.md` and reports breakage. It **detects + reports + proposes fixes for approval — it must NEVER auto-deploy to the live app.** Run it via the `/loop` skill (the exact prompt is in `docs/qa-sjekkliste.md`).
- Engine: Playwright, `e2e/*.e2e.ts`, three projects (`setup` → login, `public` → no-auth, `authed` → uses the saved session). Config: `playwright.config.ts`.
- `npm run qa` targets local dev (auto-starts/reuses the dev server); `npm run qa:prod` runs the read-only subset against live mycelet.com.
- Needs a dedicated QA user (`npm run qa:setup`, idempotent; writes `QA_TEST_EMAIL`/`QA_TEST_PASSWORD` to `.env.local`). Authed tests skip cleanly if it's missing.
- Keep authed tests **read-only** — there's one Supabase project (no staging), so writes hit prod. Write flows (post forum, save finding, real AI upload) stay manual (🖐️ in the checklist). Usage measurement (`<RegistrerBruksdag>` → `bruksdager`) skips `navigator.webdriver` browsers for the same reason — don't remove that guard.
- **Gotcha:** `/soppforhold` server-renders by fetching its own `/api/prediction/regions`, so `SOPPFORHOLD_BASE` must point at localhost in dev. It used to be hardcoded to production, which meant the page showed prod data no matter what you changed locally — a verdict change gave a fresh API response and a stale page on the same machine, and the fix looked like it hadn't worked. Preview deploys still read production on purpose (a build fetching its own not-yet-deployed URL is chicken-and-egg).
- **Gotcha:** Next/Turbopack does NOT run middleware in local dev, so middleware-only auth gating (`/profile`, `/admin`, `/forum/new`) can't be tested locally — those assertions skip on `npm run qa` and run on `npm run qa:prod` (prod has real middleware). Page-level `redirect()` gating (`/mine-steder`, `/map`, `/identifiseringer`, `/forum/moderation`) works in both — **but assert on the final URL in a browser, never on the HTTP status.** `/map`, `/mine-steder`, `/profile` and `/identifiseringer` have a `loading.tsx` since Nov 2026, so the response is already streaming the skeleton when the page calls `redirect()`: locally that arrives as a **200 plus a client-side redirect**, not a 307. `page.goto` + `toHaveURL(/auth\/login/)` (what `e2e/auth-pages.e2e.ts` does) still passes; `request.get()` or `curl -I` sees 200 and looks like broken gating. In production the middleware redirects before the page starts, so the status is real there. See «`loading.tsx` makes the route stream» under Framework quirks.

**Recent-feedback sweep (do this every time the owner reports a bug):** (1) fix the reported bug; (2) audit the WHOLE app for siblings of that bug-class (same wrong assumption/pattern elsewhere); (3) fix the siblings + verify with `npm run build` (delete iCloud `* 2.ts` dupes first — see below); (4) deploy only when the owner says OK. Proven value: the Swedish-blank-map bug's sibling was the Göteborg region-routing bug — both Norway-centric assumptions.

## Architecture

**App Router layout.** UI lives under `src/app/`. API routes are colocated under `src/app/api/<name>/route.ts`. Pages and routes share the same Next.js conventions; treat `route.ts` as the API contract.

**Supabase client split** (`src/lib/supabase/`):
- `client.ts` — browser client (anon key). Used in `'use client'` components and hooks.
- `server.ts` — server client with cookie-based session. Used in server components and route handlers. Note: `cookies()` is async in Next 15+; the server client awaits the promise inside its callbacks so call sites can stay synchronous.
- `middleware.ts` — session refresh + route gating + per-request correlation ID. The root `middleware.ts` re-exports it.
- `admin.ts` — service-role client. Server-only, never import from client code. Requires `SUPABASE_SERVICE_ROLE_KEY` in env.

**Auth gating** lives in `src/lib/supabase/middleware.ts`. The `PROTECTED_PATHS` array there is the source of truth for which routes redirect unauthenticated users to `/auth/login?redirect=…`. Add new protected routes by editing that list.

**Password reset is our own mail, not Supabase's.** `/auth/forgot` posts to `POST /api/auth/glemt-passord`, which calls `auth.admin.generateLink({type:'recovery'})` and mails `https://www.mycelet.com/auth/reset?token_hash=…` through Resend (nb/sv, `src/lib/auth/glemt-passord-epost.ts`). `/auth/reset` redeems it with `verifyOtp` **on submit, not on load** (mail scanners must not burn the one-time token) and works in any browser. Supabase's own recovery mail is a PKCE `?code=` that only works in the browser that requested it — from the iOS shell the link always opens in Safari, so app users could never reset. The route always answers 200 and treats an unknown address, a bad body and a hit rate limit alike (no account enumeration), rate-limits per client and per address (generateLink bypasses Supabase's own mail throttle) and never logs the token or address. **It has two different fallbacks, because `generateLink` stamps `recovery_sent_at` and Supabase's own `/recover` then answers 429 for 60 s:** `fallback: true` means no link was made (service-role key or Resend not configured, or `generateLink` failed) — the form calls `resetPasswordForEmail` at once, and the `?code=` path on `/auth/reset` is kept for that. `sendFailed: true` means the link was made but the mail did not go out (one retry after 1 s with the same Resend idempotency key) — the form must not chain `resetPasswordForEmail` (it would get the 429, and every new call to the route re-stamps), so it says «vent et minutt og prøv igjen» and sends the next attempt straight to Supabase without calling the route. Answering `fallback` for both would take password reset down for everyone for as long as Resend fails. On `/auth/reset`, only a 4xx answer other than 429 from `verifyOtp` means the link is dead: auth-js also returns network failures, 429 and 5xx in `error` (`erForbigaaendeAuthFeil` in `src/lib/auth/auth-feil.ts`), and those keep the token and the form. The consumed token is dropped from sessionStorage as soon as `verifyOtp` succeeds, so a reload finds the recovery session instead of retrying a used token. Do not add `recovery` to `/auth/confirm`; that route discards the session on purpose. App-created accounts (`user_metadata.plattform`) that finish the reset in Safari are signed out there and told to open the app.

**«Send bekreftelsen på nytt» depends on a dashboard template.** The button on `/auth/login` calls `supabase.auth.resend({type:'signup'})`, and auth-js sends no `code_challenge` there, so the resent link is not a PKCE link like the first one from `signUp`. That is fine only while the Supabase «Confirm signup» template points at `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup` (`src/app/auth/confirm/route.ts` redeems both kinds in any browser). With `{{ .ConfirmationURL }}` the resent link would be implicit-flow and leave the session in the URL fragment of a page that never reads it — then move the resend server-side (`generateLink` + our own mail to `/auth/confirm`, as the purre cron does). A confirmation link that still goes through `/auth/callback` and is expired, used or superseded arrives there without `code` and with `error_code=otp_expired`; the callback sends exactly that case to `/auth/login?linkExpired=1` (a cancelled Google sign-in also arrives without `code` and must not get that notice).

**Auth errors are mapped, never shown raw** (`authFeilNokkel` in `src/lib/auth/auth-feil.ts` → the `AuthErrors` namespace). Login, forgot and reset printed `err.message`; an AuthError *is* an Error, so the translated fallbacks never fired, and Norwegian and Swedish users got «Invalid login credentials» on the one screen every returning user meets. An unknown error maps to `null`, the page shows its own general text, and `varsleUkjentAuthFeil` logs code, name and status only — the message can contain the address. The same file's `erForbigaaendeAuthFeil` is the rule for «did the server actually refuse, or did no usable answer come?»: auth-js puts network failures, 429 and 5xx in `error`, and code that reads any `error` as a verdict throws away a valid reset token — or, in the Stripe webhook, would have cancelled a paying customer (see «Calls out of the billing handlers»).

**The date line on the plan card** (`periodelinje` in `src/lib/billing/kanal.ts`, shown on `/pricing` and `/profile`) says what the date means for the channel the plan was bought in. Two App Store rules: a trial shows the cancel deadline — trial end minus 24 h, the same `avslutningsfrist()` the reminder mail uses — for as long as that deadline is ahead, and «Første belastning senest {date}» after it (which is also what a three-minute sandbox trial gets), never Stripe's «Første belastning {trial end}», because Apple attempts the charge during the last 24 h; and «Sagt opp – … du belastes ikke igjen» is promised only when the row's last RevenueCat event (`metadata.rc_event_type`) was `CANCELLATION`, because `BILLING_ISSUE` with a grace period writes the same `active` + `cancel_at_period_end` while Apple keeps retrying the charge. That reading is only safe because the webhook never *writes* the CANCELLATION RevenueCat sends alongside a billing problem (next paragraph) — the comment «Kjent grense» in `kanal.ts` describes the hole as it was before that. Dates are formatted in Europe/Oslo by `periodelinjeVerdier` — `/profile` renders on a UTC server.

**A RevenueCat billing problem is two events, and only one may write.** A failed renewal fires `BILLING_ISSUE` *and* a `CANCELLATION` with `cancel_reason = BILLING_ERROR`, generated together (RevenueCat documents the pair, and that arrival order is not guaranteed). Only `BILLING_ISSUE` carries `grace_period_expiration_at_ms` (documented); the CANCELLATION has just `expiration_at_ms`, the period's own expiry, which has already passed when the pair is sent (RevenueCat's sample `BILLING_ISSUE` shows it five hours before the event time — the docs do not show a `BILLING_ERROR` cancellation, so check a real pair in RevenueCat's event history the first time one occurs). Until Nov 2026 the webhook mapped that CANCELLATION like a voluntary one («auto-renew off, access to the period end»), and Apple's grace period was lost in **both** orders: BILLING_ISSUE first → the grace end was overwritten with a past date, so the customer lost Premium the moment the grace period began; CANCELLATION first → it moved the ordering mark (`rc_event_timestamp_ms`) past the BILLING_ISSUE generated a moment earlier, which the stale-event guard then dropped. `mapRevenueCatEvent` now ACKs it (`BILLING_ERROR_CANCELLATION_ACK`) — an ACK writes neither the row nor the ordering mark, which is what makes the two orders converge — and `BILLING_ISSUE` owns the state (grace period → access to its end; none → `past_due`) until `RENEWAL` or `EXPIRATION` settles it. `BILLING_ISSUE` with a grace period keeps `trialing` when `period_type` is `TRIAL`: the first charge after a trial failed, no money has moved, and `active` with a running period is «betalende» in the daily report. The route tests replay each chain against one row in both orders (`src/app/api/revenuecat/webhook/__tests__/route.test.ts`), including the two rules a change here must never weaken: a manual grant is a floor no store event can lower, and a voluntary CANCELLATION during a TRIAL keeps `trialing`.

**Calls out of the billing handlers have deadlines, and «no answer» is never read as an answer.** The Stripe SDK waits 80 s per attempt with one retry, and Supabase Auth's admin API and `sendEpost` wait until the platform kills the function — long after Stripe or RevenueCat has given up and queued the event again. The Stripe webhook passes `STRIPE_KALL` (10 s, one retry) on every Stripe API call and wraps `getUserById` and the trial-reminder mail in `medFrist` (8 s). `/api/billing/status` runs its Stripe lookup for every free user on every page that shows plan state, so one slow day at Stripe held the header, the trial sheet and the pricing page for everyone who does not pay; it now gives each call 4 s and the whole lookup 5 s, and then answers what a Stripe failure answers (the trial as default — the best-effort rule in `tidligere-abonnent.ts`). `maxDuration` is the net under the database calls: 60 for the Stripe webhook, 30 for RevenueCat's (RevenueCat disconnects after 60 s), 15 for the status route. A missed deadline must land where a failure already lands, and that exposed one failure that landed wrong: the Stripe webhook's `brukerFinnes` answered «deleted» on *any* error, and «deleted» cancels the customer's running subscription at Stripe. auth-js returns network failures, 429 and 5xx in `error`, so a short Supabase Auth outage during a renewal would have cancelled a paying customer. Only an explicit 404 is «deleted» now — stricter than `erForbigaaendeAuthFeil`, because 401/403 mean *we* could not ask, not that the user is gone — and everything else goes the normal path, where a truly deleted user fails loudly on the foreign key and Stripe retries. Error bodies follow the same line: `/api/billing/status` never returns exception text and localizes its error (the pricing page shows it to the customer), the Stripe webhook returns the text only once the signature is verified, and RevenueCat's catch is only reachable after authorization. Still open, and each belongs in one place rather than in every caller: the logged-in home page (`src/app/page.tsx`) runs the same `harHattTilgangFor` lookup as the status route for every free user on every render, and `/api/billing/checkout` and `/api/billing/portal` call Stripe while the customer watches a spinner — all three with the SDK default (80 s per attempt, one retry). A client-wide default belongs in `getStripeServerClient` (`src/lib/stripe/server.ts`), with the per-call options above staying as the tighter ones; and the Supabase database calls have no per-call deadline — that belongs in `createAdminClient` (a `fetch` with a timeout).

**Billing/capabilities** (`src/lib/billing/`). `getBillingCapabilities(subscription)` derives `{tier, status, paid, aiDailyLimit}` from the `billing_subscriptions` row (or null). Routes that gate features call this — see `src/app/api/identify/route.ts` and `src/app/api/prediction/route.ts` for the pattern. Free users get capped/coarsened data, paid users get full detail.

**Prediction endpoint** (`src/app/api/prediction/route.ts`) has two paths:
1. **Primary:** query `prediction_tiles` table via the `get_prediction_tiles_in_bounds` RPC. Tiles are generated nightly by `/api/cron/generate-tiles?country=NO|SE` (schedules in `vercel.json`, 01:15/01:45 UTC).
2. **Fallback:** when no tiles exist for the date/area, computes a score from `fetchWeatherSummary()` + historical findings. Returns 502 if no weather provider is reachable for the region.

When `?speciesId=N` is set, the route applies a per-species multiplier from `src/lib/utils/species-scoring.ts` to the final score (see "Per-species scoring" below).

**Weather adapters** (`src/lib/weather/index.ts`). Single export `fetchWeatherSummary({lat, lon})` that routes by region:
- `'NO'` → MET Norway Frost (requires `MET_FROST_CLIENT_ID`; placeholder is a no-op stub)
- `'SE'` → SMHI Open Data (no key required)
- `'other'` → OpenWeather (requires `OPENWEATHER_API_KEY`)
- Returns `null` if no provider is configured/reachable for that region.

Region detection in `src/lib/utils/region.ts` — bounding-box check, returns `'NO' | 'SE' | 'other'`.

**Three distributions, one 0–100 label.** The same-looking score has different distributions depending on the surface, and each needs its own ladder. A raster *cell* (`cell-score.ts`) is graded by `CONDITION_THRESHOLDS`; a *region* on `/soppforhold` is the 90th percentile over cells and is graded by `REGION_CONDITION_THRESHOLDS` (`src/lib/prediction/region-score.ts`), measured at p90/p75/median of 374 real region-days; the *point day-score* from `mushroom-day.ts` has its own `forecast-scale.ts` bands. Mixing them is a real bug that shipped: the region endpoint reused the per-cell ladder, so a verdict promising "top 10%" fired on 22.5% of region-days, and the colour came from a third ladder entirely — the same number could get the peak verdict in text and an amber dot beside it. Recalibrate with `npm run calibrate:regionterskler` after the season; the current basis is a 17-day August window. The alert threshold (`VARSEL_MIN_SCORE` in `src/lib/alerts/decision.ts`) is bound to the region ladder's `excellent` for the same reason: it used to import the point-scale `FORECAST_GREEN_MIN` (85), which on the region distribution is the top 12 % of days — 7 of 22 regions (Oslo, Stockholm) never reached it in a month, so alerts and X posts were silent in the biggest markets. The Sunday X post (`byggUkesPost` in `src/lib/x/innlegg.ts`) reads the same ladder the other way: it stays silent when the best region is under `moderate` (the median region-day). Its only condition used to be a non-empty list, so «best an ligger Bergen (4 av 100)» went out every Sunday all winter.

**One season state** (`src/lib/sesong/sesongtilstand.ts`). `sesongtilstand(naa)` is the only answer to «where in the mushroom year are we?»: Oslo time, the date injected, phases `forsesong` (Jun–Jul), `hoysesong` (Aug–Oct), `ettersesong` (Nov), `vinter` (Dec–Mar), `var` (Apr–May). Before it no surface knew what month it was — in November the pricing page said high season was under way, the trial sheet sold «resten av høsten», the home card told people twice to come back in late summer, and `/soppforhold` wrote that a species «er i sesong her nå» beside 3/100. Four rules. (1) It is the **calendar, not the conditions**: a dry August is still `hoysesong`, so a surface that says something about conditions must also read the numbers (`innledningsTilstand` in `src/app/soppforhold/hent-regioner.ts` requires both low scores and `!iHovedsesong` before it says «utenom sesongen»). (2) **«Hovedsesong» is the code's word, not the copy's.** `iHovedsesong` means June–November (season weight above zero), but to the user «hovedsesong» / «högsäsong» means August–October — the tick «Hovedsesong for sopp i Norge» first appears on 1 August. The off-season text once pasted the constant's name into the copy and told Swedish users «Högsäsongen börjar i juni». Write «soppsesongen starter i juni, med høysesong fra august», and use `erHoysesong` for what the user calls hovedsesong. (3) Off-season copy has one source, `src/lib/sesong/utenom-sesong-tekst.ts` (two copies rendered the same sentence twice in one card for half the year), and it never says «kom tilbake» — that is telling people who paid for a year to leave. (4) The month table is written out rather than imported, because the file is used in client components (pricing, trial sheet); `sesongtilstand.test.ts` locks it to `SEASON_WEIGHT_BY_MONTH` in `mushroom-day.ts` for all twelve months. «Is this species in season?» is a separate question with its own single answer, `erArtISesong` (`src/lib/sesong/art-i-sesong.ts`): the calendar's window (`baseSeasonMask`), with `null` meaning unknown, not «out». The regions endpoint used the narrow catalogue months alone and said «utenfor sesong» about the species the raster itself ranked first (piggsopp in August), so `/soppforhold` dropped the species line in mid-season. Purchase surfaces take their season lines from `src/lib/billing/sesongtekst.ts`, which returns keys only for the months the claim is true.

**SR16 lookups are header-keyed.** NIBIO's GetFeatureInfo omits a layer's whole sub-document when it is nodata at the pixel (it does not return −9999), so a positional parse shifts every later value — the original parser read standing volume as site index in 0–14 % of forest cells, which cleared the rich-soil bonus and corrupted the soil factor in the nightly tiles. `parseSr16Html` keys on the «Skogressurskart (<LAYER> raster)» headers (normalising NIBIO's `SSRVOLMB` typo). Cells with treslag nodata but bonitet/volume present are forest and are kept as `ukjent`. Background and the patch-level signal study: `docs/mikro-prediksjon-gjennomgang.md`.

**Forest is sampled at up to five points per grid cell.** SR16 and CORINE are point lookups, and every grid — the nightly raster, `/api/prediction/grid` and `/api/prediction/species-spots` — used to look up only the cell centre and drop the whole cell when that point was water, a field, a road or a settlement, leaving holes over forested land (Oslo map, 15 Sep 2026: Nesodden's east coast, east of Lørenskog, around Enebakk). All three now go through `provSkogIRuter` (`src/lib/prediction/skogprover.ts`): every centre first, then for misses the four quadrant centres (±step/4) in fixed order, first hit wins; cells with no forest at any of the five points stay honest holes (lakes, the fjord, city centres). The cell keeps its centre — grid position, score inputs and pin are unchanged; only the forest data comes from the offset point, which tiles record as `metadata.skogprove` (`senter` | `forskjovet`) + `skogprove_lat`/`skogprove_lng` and which `nearestForestTile`, the grid's area report and the pin explanations in both live grids use for the distance. The pin text must get `skogavstandKm(cell, prove)` — null only when the forest was measured at the centre, because `null` is what prints «Skog her» (and `0` would print «0 m unna»); a live-grid quadrant centre is several km from the pin. Measured live with `npm run dekning:rutenett` (no writes): Oslo 53 → 76 of 84 cells, Bergen 16 → 35 of 40, all of Norway 181 → 317 of 399, Sweden 219 → 354 of 420 uncapped. Offsets run in rounds (first quadrant for every miss, then the second…) so a cap spreads over the region instead of being spent on the first cells and on lakes. They are bounded per region by `EKSTRA_SKOGOPPSLAG_PER_RUTE` (no real cap for SR16; 0.65 per cell for CORINE, which is ~10× slower — ~99 of Sweden's 135 recoverable cells) and by a deadline that reserves time for the remaining regions' centres (`skogproveFrist`); cells cut short are logged as `generate_tiles.skogprove_avkortet`, never dropped silently. The live grids stop starting offset lookups 6 s into the forest phase, so a struggling NIBIO is not hit four times harder.

**Per-species scoring** (`src/lib/utils/species-scoring.ts`). When a specific species is requested, multiply the base prediction score by `computeSpeciesAdjustment(species, weather, month)` — multiplier in `[0.05, 1.3]`. Out-of-season collapses to ~0.05; peak season + optimal weather hits 1.2-1.3. Genus profiles in `GENUS_PREFERENCES` cover Cantharellus, Boletus, Hydnum, Suillus, Agaricus, Amanita, Cortinarius and ~7 more; unknown genera fall back to a generic profile. Calibrated by hand from field knowledge — should be tuned against real finding data when available.

**Species data flow.** The list view (`src/app/species/page.tsx` → `useSpecies` hook) reads `primary_image_url` denormalized on `mushroom_species`. The detail view (`src/app/species/[id]/page.tsx`) reads from `species_photos` joined by `species_id`. When seeding photos, write to both: `mushroom_species.primary_image_url` for the list, `species_photos` rows for the detail page.

**Photo attribution.** Every species photo is a Wikimedia Commons file under CC BY / CC BY-SA — licenses that require naming the photographer and the license wherever the image is shown. The credit lives beside the URL in both tables: `species_photos.{photographer,license,source_url}` and the denormalized `mushroom_species.primary_image_{photographer,license,source_url}` (migration 062, originally numbered 055 — renumbered because two files shared 055). Backfill both from the Commons API with `node --env-file=.env.local scripts/backfill-photo-credits.mjs` — dry-run by default, `--apply` to write, idempotent, and it never overwrites a hand-set credit without `--force`. Render with `<PhotoCredit>` (`src/components/ui/PhotoCredit.tsx`); it stays silent on placeholder values, because the pre-backfill seed wrote `license = 'Wikimedia Commons'` — a *source*, not a license — and rendering that would be a false licensing claim. Kindwise's `similar_images` carry no credit we can pass on, so they must never inherit one.

**Sanketips articles + AEO.** Source of truth is markdown in `content/sanketips/`; `node scripts/build-articles.mjs` renders `public/landing/sanketips/*.html` AND writes `src/lib/sanketips/manifest.generated.ts` + `fulltekst.generated.ts`, which feed `sitemap.xml`, `/llms.txt` and `/llms-full.txt`. Never hand-list articles anywhere. Each article ends with an H2 «Spørsmål og svar» (sv: «Frågor och svar») of H3 questions + one-paragraph answers drawn from the article itself — rendered visibly and emitted as FAQPage JSON-LD. `ORGANISASJON` in `src/lib/seo/organisasjon.ts` is the single Organization schema (the build script mirrors it; `src/lib/sanketips/__tests__/manifest.test.ts` catches drift). Status and owner tasks in `docs/aeo.md`.

**Map and offline.** Leaflet via `react-leaflet@5`. Service worker + offline tile cache live behind premium gating (see `docs/offline-map-mvp.md`). The `/map` page is a Server Component; the actual map is dynamic-imported with `ssr: false` via the thin client wrapper at `src/components/map/MushroomMapLazy.tsx` (Next 15+ disallows `ssr: false` in Server Components).

**Visibility model for findings.** `findings` rows have `visibility` (`public` | `approximate` | `private`) and an `is_zone_finding` flag. The `set_display_location` trigger computes `display_latitude/longitude` based on those fields — randomized for `approximate`, grid-snapped for zone findings, NULL for private. Views like `public_findings` and APIs use the display columns, never raw `latitude/longitude`. If you change visibility logic, update both the trigger and the view.

**A user's point leaves the server rounded.** External place lookups (weather, forest, elevation) get `roundForProviderLookup(lat, lon)` (`src/lib/privacy/provider-precision.ts`): three decimals, about 110 m — still inside the box NIBIO queries with and far under the distance to the nearest weather station, so the answer is the same. `/api/findings` once passed the untouched point of every saved finding, private ones included, to MET Frost, NIBIO, Kartverket and CORINE, where a secret spot settled in four institutions' access logs; `/api/spot-feedback` was fixed in the same round, and `/api/prediction` — whose point is the device's GPS position or the map centre, often exactly where the user is standing — was the sibling forgotten until Nov 2026. The math that never leaves the server (bounding box, nearest tile, finding density) keeps the exact point, the `prediction.start` log line gets two decimals (server logs must not hold a position trail), and Kindwise gets `coarsenLocation` (`src/lib/privacy/coarsen-location.ts`, 0.1° cells) instead, because there the point is to be hidden, not merely trimmed. A new route that hands a user's coordinates to a provider must round first; only `/api/prediction` has a route test for it (`oppslagspresisjon.test.ts`).

## Cross-cutting infrastructure

**Logging** (`src/lib/log/`). Five-level structured logger: `trace < debug < info < warn < error`. Default level is `debug` in dev, `info` in prod; override with `LOG_LEVEL` env. Output is pretty single-line in dev, JSON object per line in prod (Vercel/Sentry-ingestible).

Use `createRequestLogger(request)` in route handlers to get a child logger pre-bound with `reqId` (correlation ID propagated via the `x-request-id` request header set by middleware) and `route`. PII is auto-redacted — emails masked, secret-pattern keys (password/token/apikey/authorization/etc.) replaced with `<redacted>`. UUIDs and numeric IDs pass through (internal-only, useful for cross-referencing).

See `docs/logging.md` for the full conceptual model + the documented Next 14+ quirk where middleware-set response headers don't propagate to the client (only the request-header rewrite half works; server-side correlation is unaffected).

**Audit log** (`src/lib/audit/log.ts` + `admin_audit_log` table from migration 008). Append-only by trigger — UPDATE/DELETE blocked at the DB layer even for the service role. Use `logAdminAction({actorId, action, targetUserId, metadata, request})` for compliance-relevant events: admin role changes, account deletion, etc. Currently wired into `/api/admin/verified-foragers` (POST + DELETE), `/api/admin/moderation` (every action, as `moderation.<action>`) and `/api/me/delete`. The helper is failure-safe — if the service role key isn't set or the migration isn't applied, the underlying action still succeeds and a warning hits the server console.

**Forum moderation** (`/forum/moderation` → `GET`/`POST /api/admin/moderation`, pure logic in `src/lib/moderation/moderering.ts`). Until Nov 2026 a moderator could only change a report's status: the console never showed what was reported, and nothing in the app could hide a post — the only UPDATE policies on `forum_posts` and `comments` are owner-only, so dangerous advice about a deadly look-alike could be removed only with hand-written SQL, while Apple (guideline 1.2) expects a report to be acted on within 24 h. The route checks `moderator_roles` with the session client (a failed lookup is «no») and does the work with the admin client, because hidden rows — and rows by authors the moderator has blocked — are invisible through RLS. `POST` takes only `{reportId, action}`: the target is **always derived from the report row on the server**, never from a client-supplied table or id, so the route cannot be used to hide arbitrary content. Actions: `hide` (sets `is_hidden`, resolves every open report on that content), `unhide` (shows it again and sends the reports the hide had resolved back to `reviewed` with `resolved_at` cleared — that date drives deletion a year later), `dismiss`, `reviewed` (seen, still open) and `resolve` (handled without hiding — the only way to close a finding report other than dismissing it). «Open» means `pending` **or** `reviewed` (`AAPNE_RAPPORTSTATUSER`) on every surface: the console's list and banner, what a hide resolves, the `/admin` card and the daily report; counting `pending` alone made a report vanish the moment someone had looked at it. **Findings cannot be hidden**: `findings` has no `is_hidden`, and `deleted_at` is the owner's own 30-day undo (the purge cron hard-deletes the row and its image), so it must not be borrowed for moderation — removing a finding needs a migration (`is_hidden` plus the `public_findings` view). What never leaves the server (`byggRapportvisning` builds each object field by field): `reporter_id`, finding coordinates raw or masked, and, for a finding, anything `public_findings` would not show its readers — the reports table does not check that the reporter could see the finding, so an id from a linked post must not become a way into someone's notes. There is no way to eject a user yet; that needs an owner decision. **Notification:** a new report used to be seen only by whoever opened the console. `hentAapneRapporter` (`src/lib/rapport/aapne-rapporter.ts`, one read-only query: count and oldest `created_at`, nothing about content or reporter) feeds the daily report — subject line, a banner above the numbers and a row, as soon as *anything* is open, because the report goes out once a day and whatever is open today is past the limit before the next one — and the `/admin` card, both using the console's own `oppsummerAapneRapporter` and `BEHANDLINGSFRIST_TIMER` so the three cannot disagree. Two smaller forum rules from the same round: readers of `public_findings` filter blocked authors with `utenBlokkerte` (`src/lib/moderation/blokkering.ts`) because the view does not know the block list that RLS applies in the forum, and a post's linked finding is read through `public_findings` (`hentKobledeFunn`), never embedded from `findings` — owner-only RLS returned `null` to everyone but the author, who could not tell.

**Rate limiting** (`src/lib/rate-limit/`). In-memory fixed-window token bucket. Use `checkRateLimit(key, limit, windowSeconds)` + `getClientKey(request, userId)` + `rateLimitResponse(result)` from `src/lib/rate-limit/route`. Applied in about 40 route handlers (`grep -rl checkRateLimit src/app/api`), e.g. `/api/identify` (20/min/user), `/api/prediction` (60/min/client), `/api/billing/checkout` (5/min/user), `/api/me/export` (10/min/user), `/api/me/delete` (5/min/user). **Per-instance only** — Vercel auto-scales horizontally, so effective limit is `N × configured`. The app is live with this limiter; replacing it with Upstash Redis or Vercel KV is still an open follow-up.

**Security headers + CSP** (`next.config.js`). Six baseline headers on every response: HSTS, X-Frame-Options: DENY (matches CSP `frame-ancestors 'none'`), X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy (camera + geolocation for self), X-XSS-Protection: 0. Plus an **enforcing** `Content-Security-Policy` (flipped from report-only in June 2026) with allowlists for Stripe, Supabase, Wikimedia, Kindwise, Kartverket, OSM, GA4. A new third-party host MUST be added to the allowlist before deploy — otherwise the browser blocks it silently (no report-only safety net any more).

**Paying, trials and gift passes (daily report and /admin).** One rule — `klassifiserAbonnement` in `src/lib/rapport/abonnement.ts` — feeds both the daily report and the `/admin` statistics page; each row lands in exactly one of `betalende` / `prove` / `gratisTildelt` / `utlopt` / `inaktiv`. «Betalende» is a store row (Stripe or App Store) with status `active` and a running period, whatever its tier (see below). `trialing` is *not* «betalende» and has its own block (løpende, startet 7 d, til første belastning, avbrutt). Rows marked `metadata.source = 'manual_grant'`, rows without a store provider and rows owned by internal `@mycelet.com` accounts are «gratis tildelt», never sales. `/admin` had its own loop until PR #266 (Oct 2026); on 15 Sep 2026 it showed 8 paying where the truth was 1 (three trials, three grants, a Stripe row that expired in July). For a store row the *status* decides, not the tier: «trialing» is «prøve» and «active» with a running period is «betalende» even when the tier is `free` (an unknown Stripe price ID — the webhook keeps only an *existing* paid tier), because Stripe and the App Store say active only after money moved; for a manually inserted row the tier decides («gratis tildelt» or «inaktiv»). Such rows are also counted in `ukjentPlan`, which the report and /admin print as a ⚠️ line — the customer has paid or is trialing but `hasPaidAccess` gives no Premium — and which must be 0. The trial block (startet 7 d, gikk til betaling, avbrutt) counts on the same `erButikkrad` rows, so it can never disagree with the classifier about which rows exist. Reporting only: Premium access still goes through `hasPaidAccess`, where trials and grants do unlock features. Both webhooks stamp `metadata.prove_start` when a row first becomes trialing and `metadata.forste_belastning` when a trial converts to a paid `active` (`oppdaterProveMerker` in `src/lib/billing/prove-merke.ts`) — needed because both webhooks rebuild `metadata` on every write. A RevenueCat CANCELLATION during a TRIAL keeps `trialing` so a cancelled free week never reads as a customer, and so does a `BILLING_ISSUE` with a grace period during a TRIAL (the first charge failed; see «A RevenueCat billing problem is two events»).

**App Store trial reminder** (`prove_paaminnelser` + `prove_svar`, migration 072; cron `/api/cron/prove-paaminnelse-app` 06:30 UTC daily). Apple sends nothing before an intro offer converts, so unlike the web (Stripe's `trial_will_end` → the webhook's e-mail) the day is computed here: RevenueCat-owned `trialing` rows that are not `SANDBOX` and not `cancel_at_period_end` get `byggAppProvePaaminnelseEpost` when `current_period_end` (as Oslo date) is 3 days ahead, or 2 as a catch-up, never 1 or 0 (`bestemAppProvePaaminnelse` in `src/lib/billing/prove-paaminnelse-app.ts`). The sent marker lives in its own table keyed by `(user_id, kanal, prove_slutt)` because both webhooks rebuild `metadata` on every write; the cron **reserves the row before sending** (a `23505` on insert means another run took it → skip) and deletes it when the send fails, so a failed send retries next morning, at most once more inside the window — marking *after* the send was not safe, because Resend's idempotency key lives 24 h and the cron runs every 24 h. A missing table means warn-and-skip, never send. Three honesty rules in the copy: it never states an amount (the RevenueCat webhook stores no price or currency, and the App Store price is set per country by Apple, so it says «prisen som sto i appen da du startet» and must never take a number from `plans.ts`); the cancel deadline is `current_period_end − 24 h` as an Oslo day and floored hour («senest 26. september kl. 07», «senest i morgen kl. 07» on the catch-up day) because Apple attempts the renewal within the last 24 h, and the path is Apple's real one — «Innstillinger → navnet ditt øverst → Abonnementer» plus `APPLE_ABONNEMENT_URL`, never «Apple-ID», which is no longer a row or a name; and «gratisuka»/«gratisvecka» is used only when `current_period_start → current_period_end` is 6–8 days (`erGratisuke`), otherwise the web wording «prøveperioden» verbatim, since offer codes can be 3 days or a month. The one-tap question at the end links to `GET /api/prove/svar?t=…&valg=…` with an HMAC token over user id, trial end **and send time**, derived from `SUPABASE_SERVICE_ROLE_KEY` (`src/lib/billing/prove-svar-token.ts`); the route writes on GET only for a real navigation (`Sec-Fetch-Dest: document` + `Sec-Fetch-Mode: navigate`) at least `AKTIVERING_MIN_MS` after the send, otherwise it shows the same page with one button and writes on the `POST` — mail-link scanners fetch all three links within seconds and would otherwise record «ai» for people who never opened the mail. Answers land in `prove_svar` and appear in the daily report as «Svar fra prøvestartere (7 d)». Both tables are personal data: `/api/me/export` carries them as `trialReminders` and `trialAnswers` (admin client, schema 7) and `/personvern` names them under betalingsdata.

**Rapportpuls** (`rapportpuls`, migration 069; retired 17 Sep 2026 — the 04:40 UTC cron is gone from `vercel.json`, and the route `/api/cron/rapportpuls`, `src/lib/rapportpuls/` and the optional `puls` argument of the alert e-mail and the X flip post were deleted in Nov 2026, so nothing can write or print it; only the table and migration 069 remain as history). It compared, per region, GBIF fungi records in the window `[day−13, day−7]` with the mean of the same window in 2023–25. **Not shown to customers since 17 Sep 2026** — the alert e-mail and the X flip post no longer receive it. The original lag reasoning was wrong: the gap is not GBIF ingestion but people entering finds into Artsobservasjoner weeks to months after the trip (by mid-September only 57–74 % of a year's August records exist; ~95 % by New Year). Comparing an unfinished current window with finished prior years therefore reads «under» almost everywhere every autumn (Kristiansand −92 % went out in two alert e-mails on 15–16 Sep), and the small region boxes are dominated by single recorders (Stavanger +555 % on a baseline of 20). A fair comparison counts prior years *as they stood on the same date*, using Artsobservasjoner's sighting id (GBIF `catalogNumber`, dataset `b124e1e0-4755-430f-9eab-894f25a9b59c`), which rises in entry order. Never re-expose a year-over-year number outside the owner's report without that same-date baseline.

**Soppregistreringer, same date as before** (`soppregistreringer`, migration 071; cron `/api/cron/soppregistreringer` 05:45 UTC daily). Answers «is there less mushroom this year, and where?» for the owner's daily report without the entry-lag lie: people enter finds into Artsobservasjoner weeks to months after the trip (mid-September holds only 57–74 % of a year's August records, ~95 % by 1 January), so raw 2026 vs finished 2023–25 always reads as a slump. Artsobservasjoner's sighting id (GBIF `catalogNumber`) rises in *entry* order, so prior years are counted **as they stood on the same date**: for year Y the cutoff is the highest id among the dataset's records with `modified` = Y-MM-DD, where MM-DD is the current GBIF snapshot (dataset `pubDate`); 2023–25 count only ids ≤ cutoff, this year counts everything, normal = mean of the three. Windows «sesongen hittil» (1 Aug → snapshot − 7 d) and «siste hele uke» (the 7 days ending there), Norway + the 15 counties of 2024 built from GBIF's GADM 3.6 facet (never `stateProvince`), groups `alle` (taxonKey 5) and `storsopp` (Agaricales/Boletales/Russulales/Cantharellales). Pure logic in `src/lib/rapport/soppregistreringer.ts`; fetching in `soppregistreringer-henting.ts` — 64 GBIF calls because county × group × window come from intersecting id sets instead of separate calls, 2 s between calls (faster gives 429), ~150–210 s, 270 s deadline; every catalogNumber facet (counts *and* cutoffs) stops the run when it hits `facetLimit` or covers < 99 % of `count`, because a truncated facet drops the highest ids and looks fine. **`/process` saying `FINISHED` means nothing for the index:** it describes the download, finishes a minute after the crawl starts, and its newest entry is often a `NOT_MODIFIED` no-op (12 Sep edition: crawl 11:28, `pubDate` 11:35, no-op `FINISHED` 11:36, search index 13:22). `sjekkIndeksering` therefore fails closed unless the newest `NORMAL` crawl attempt has a `/pipelines/history` entry, no `INTERPRETED_TO_INDEX` of that attempt is running, and the crawl's own `INTERPRETED_TO_INDEX` is `COMPLETED` *after* the dataset's `modified`. The weekly crawl runs Sundays ~03:00–03:35 UTC and indexing finishes ~05:00–05:20, hence 05:45 (before the 06:00 report); a night the gate says no costs nothing, a wrong snapshot would stand for a week. If the count runs out or GBIF fails twice nothing is written and the next night redoes the whole snapshot (one upsert of 64 rows; a row for the snapshot means done). `tynt` (*) = normal < 50 or the three years differ by more than 3× (a few recorders). Dry run against live GBIF, no DB: `npm run torrkjor:soppregistreringer -- --til=2026-09-07` (verified 17 Sep 2026: Norway 92 %, storsopp 86 %, all 15 counties within ±5 points of an independent count). These are **recording activity, not mushroom quantity** — shown only in the owner's report with its fixed caveat, never to customers, never in alerts or X posts. The block replaced the rapportpuls line in the daily report; with the alert e-mail and X posts no longer reading `rapportpuls` either, its 04:40 cron, route and lib were removed and the table is history. The same report row «Nye kontoer (14 d) som følger et område» links account-less alert rows to accounts by lower-cased e-mail in memory only; no address reaches the report, log or JSON.

**AI-identifiseringen is monitored, because it died silently once.** Kindwise takes `details` and `language` as **query params**; in the body it answers 400 «Unknown modifier», and from May to 29 Sep 2026 every call did exactly that while the user saw «Identifikasjon feilet» — `ai_identifications` (migration 020) got a row only for a call that succeeded, Sentry drops kindwise.com on purpose, so «nobody uses it» and «it is dead» were the same zero for four months with 2 050 credits untouched. Three things now make that visible: `kindwise-request-shape.test.ts` locks the request form; every failed Kindwise call writes one row (a status code only, no user id) to `ai_identifiseringsfeil` (migration 073, purged after 30 days) — the HTTP status Kindwise answered with (the response body goes to the log), or **status 0 when no answer ever came** (timeout, DNS, a reset connection, a body that stops half-way); and `src/lib/identifications/kindwise-status.ts` reads Kindwise's `usage_info` (costs no credits) for `/api/health` (`checks.ai`, non-fast only, cached 5 min, reported but never a 503 — the key is never set locally) and for the daily report's «AI-identifisering» block, which raises `ai.varsel` when calls fail without any succeeding, when Kindwise blocks the key, or when credits drop under `KINDWISE_KREDITT_VARSEL`. `scripts/sjekk-kindwise.mjs` sends the route's exact request from a laptop when the app says «Identifikasjon feilet». The status-0 row closed the same blind spot for a different failure: a `fetch` that threw went straight to the route's outer catch and was counted nowhere, so a Kindwise that hung was as invisible in the report as the four months of 400s had been.

**The free AI quota is reserved before the paid call, and every wait has a deadline.** `/api/identify` used to count the day's calls, wait seconds on Kindwise and write the `ai_identifications` row afterwards — so every request that arrived while the earlier ones were still at Kindwise saw the same number, and a free account on 4 of 5 could fire as many parallel calls as the 20/min burst limiter let through. A free account now inserts its row *first* and counts the rows in the 24 h window with id ≤ its own; over the cap, the row is deleted and the answer is `daily_quota`. The reservation is **released when the call cost nothing** (Kindwise rejected it, or never answered) and stands once Kindwise has answered OK, whatever happens afterwards — the credit is spent. Paid and trial accounts have no daily cap (the plan is sold as «ubegrenset»; a ceiling is prepared, but the number is the owner's decision and needs the price page and the terms changed in the same PR) and get their row after an OK. A row therefore still means «a credit was spent», which is what the daily report counts; the known leftover is a function killed between reservation and release (`identify.reservation_release_failed` when the delete itself fails). Deadlines: `KINDWISE_TIMEOUT_MS` (25 s, each call its own signal, also covering the body read) under the route's `maxDuration` of 60 → `provider_timeout` (504), with no automatic retry, which could cost a second credit for the same photo. The client (`src/lib/hooks/useIdentify.ts`) sends with XHR so its deadline can follow upload *progress* (`IDENTIFY_STILLSTAND_MS` without a byte moving, `IDENTIFY_SVARFRIST_MS` for the answer): a flat 75 s cap cut every attempt on a slow forest uplink, or threw away an answer the server had already paid for. It tells `upload_stalled` (nothing was spent — retry) from `timeout`/`response_lost` (the server may have done the whole job — point to the history, never invite a blind retry).

**An AI suggestion never gets a green «spiselig» stamp.** `<AiEdibilityBadge>` (`src/components/identify/AiEdibilityBadge.tsx`) keeps the toxic, deadly, inedible and unknown badges and replaces the two edible classes with a neutral «ikke matvurdert»: a warning is useful even when the species ID is wrong, a green stamp is harmful exactly then. The rule lived only in the result view; the look-alike card and the history list used a raw `<EdibilityBadge>` and stamped the same suggestion green. Use the component wherever a suggested species is shown — `edibility-asymmetry.test.ts` reads every source. Poison-centre numbers come from the `Safety` namespace through `byggGiftnummer` (Sweden has two, Norway one) and are never hardcoded at the call site.

**Health check** (`/api/health`): public, no auth. `?fast=1` skips DB checks for high-frequency probes. Returns 200 with per-check `{ok, message}` pairs covering env vars, database, audit log table presence; 503 if an uptime check (env vars, database, audit log table) fails; `checks.epost`, `checks.ai` and `checks.tabeller` are reported but never cause a 503. Wired into the logger at debug/warn levels. `checks.tabeller` (non-fast only, cached 5 min) lists tables from newer migrations that are missing (`NYERE_TABELLER` in `src/lib/supabase/tabell-finnes.ts`). **Gotcha:** a missing table arrives from PostgREST as `PGRST205`, not Postgres' `42P01`, and a HEAD count (`select(..., {count:'exact', head:true})`) against a missing table comes back as `error = null, count = null` — so `count ?? 0` turns a forgotten migration into a silent zero. Use `erManglendeTabell` / `tellRader` from that file instead of testing for `42P01`.

**Toaster** (`react-hot-toast`) is mounted in `src/components/layout/Providers.tsx` — `toast.success` / `toast.error` work app-wide.

**Every modal dialog and sheet uses `useDialogFokus`** (`src/components/ui/useDialogFokus.ts`). Each sheet was a hand-written `<div role="dialog">` where Escape did nothing, focus stayed on the button behind the backdrop, Tab wandered on into the page underneath (also under «Slett kontoen») and focus was gone after closing. The hook does four things while `aapen` is true: moves focus to the **panel** (`tabIndex={-1}`), not the first field — a focused input pulls up the iOS keyboard, and in the delete dialog the first stop would be a destructive control; closes on Escape, but only the topmost dialog and only when `kanLukkes` (the trial sheet can lie on top of the intro); keeps Tab inside the panel; and returns focus on close (never to a text field, for the keyboard's sake). Deliberately no `inert` or `aria-hidden` on the rest of the page — `aria-modal` covers screen readers, and `inert` would take the toaster, stacked sheets and the intro's promise that a scrim can never lock the app. Close buttons use `LUKKEKNAPP_KLASSER` (a 44 × 44 px target around the icon). A new modal without the hook is a regression; the hook's test file shows the expected behaviour. The one `role="dialog"` that must **not** get it is the cookie notice (`src/components/layout/CookieNotice.tsx`): it is not modal — no `aria-modal`, no scrim, a card above the bottom nav — and the app has to stay usable until it is answered. Moving focus into it or holding Tab there would turn an optional consent into a wall (the notice once covered the bottom nav, so a tap on «Kart» landed on «Tillat analyse»; a consent given by a navigation tap is not a consent).

**i18n** (`src/i18n/`, next-intl, no URL prefixes). Locale comes from the `MYCELET_LOCALE` cookie, falling back to `Accept-Language` and then `nb`. Client components use `useTranslations()` / `useLocale()` against `messages/{nb,sv}.json`; server code calls `getUserLocale()` from `src/i18n/locale.ts`.

`/soppforhold` (the app's logged-out first screen) follows the visitor's locale: copy from the `Soppforhold` namespace, verdicts and species names via `hentRegioner(locale)`, and **Sweden's section first for `sv`** (`regionerPerLand`). The area pages `/soppforhold/[omrade]` instead follow the region's *country* (Göteborg is always Swedish, with Swedish poison-centre numbers), so each shared URL has one language for crawlers.

Two gotchas that produced real Swedish-user bugs:

- **Text generated server-side is not covered by next-intl.** Anything an API route returns as prose — prediction verdicts, flush banners, habitat reasons, weekday labels, "nothing found" messages — needs the locale threaded in explicitly. The pure prediction libs (`src/lib/prediction/mushroom-day.ts`, `flush.ts`, `src/lib/utils/prediction-explanation.ts`, `src/lib/nibio/habitat.ts`) each take an optional `locale` and hold a per-language `COPY` table next to the logic; they default to `nb` so tests and pre-generated tiles are unaffected. **If a route caches its response, the locale must be part of the cache key** — otherwise the first caller's language is served to everyone.
- **Species names come from the database, not the message catalog.** Use `getSpeciesDisplayName(species, locale)` from `src/lib/utils/species-name.ts` and select `swedish_name` alongside `norwegian_name`. It falls back to Norwegian silently, so a missing `swedish_name` shows as Norwegian text rather than an error — verify new species rows have both. Source Swedish names from SLU Artdatabanken (artfakta.se / Dyntaxa, which GBIF exposes with a `preferred` flag), never by translating the Norwegian name: several Swedish mushroom names differ by only a word from a *different* species' name.

Pre-generated `prediction_tiles` store habitat reasons in **both** languages since PR #118 (`reasons` + `reasonsSv` in tile metadata), and the tile path of `/api/prediction` picks by locale — so every path is localized. Tiles older than 2026-08-02 lacked `reasonsSv`, but the raster regenerates nightly, so that gap closed itself.

## Database notes

PostGIS is required (extension created in 001). Geo queries on `findings` and `prediction_tiles` use GIST indexes on `ST_SetSRID(ST_MakePoint(lng, lat), 4326)`.

If anyone runs `DROP SCHEMA public CASCADE` to reset the database, Supabase's automatic table grants for `anon` and `authenticated` are wiped. Symptom: REST/browser queries fail with `42501 permission denied for table X` even though RLS policies look correct. Restore with:

```sql
GRANT USAGE ON SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL TABLES IN SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL FUNCTIONS IN SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO anon, authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO anon, authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON FUNCTIONS TO anon, authenticated, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON SEQUENCES TO anon, authenticated, service_role;
```

## Framework quirks worth knowing

Most of these came up during the Next 14 → 16 upgrade; the last two are Capacitor's:

- **`cookies()` is async.** Returns `Promise<ReadonlyRequestCookies>`. Either `await` it or capture the promise once at construction and `await` inside callbacks (the pattern in `src/lib/supabase/server.ts`).
- **`ssr: false` on `next/dynamic` is disallowed in Server Components.** Wrap the dynamic import in a thin `'use client'` component (see `src/components/map/MushroomMapLazy.tsx`).
- **`useSearchParams()` requires Suspense for prerendering.** Wrap pages that use it in `<Suspense>` with a fallback. Pattern: extract the hook-using body to an inner component, wrap from the default export. Already done for `/auth/login`, `/auth/register`, `/forum/new`, `/pricing`.
- **Middleware-set response headers don't propagate when a route handler builds the response.** The init-headers form `NextResponse.next({headers})` and the post-construction `response.headers.set()` both fail to reach the client. The request-header rewrite half DOES work (so `createRequestLogger` picks up `x-request-id` correctly server-side). See `docs/logging.md`.
- **`loading.tsx` makes the route stream, and a streamed response cannot change its status.** `/map`, `/mine-steder`, `/profile` and `/identifiseringer` have one (skeletons in `src/components/ui/SideSkjelett.tsx`) so a tab tap shows the shell at once — in the app on one bar of coverage, the previous screen used to stand untouched until the whole answer had arrived, and the tap looked dead. The price: once the skeleton is on its way, `redirect()` and `notFound()` can no longer set the HTTP status; the redirect becomes a 200 plus a client-side redirect (see the QA gotcha above). So never add a `loading.tsx` at the root of `src/app`, or under `species/` or `soppforhold/` — an unknown species or area would answer 200 instead of 404. Skeletons carry no text (nothing to translate) and no `<RegistrerBruksdag>` (a page that was never shown must not count as a usage day).
- **Prerender + Supabase env vars.** Pages that call `createClient()` need env vars at build time. Either keep `.env.local` populated locally during build, or mark such pages `force-dynamic` if they must run without env at build time.
- **Never run `npx cap sync` from a git worktree.** It rewrites the relative paths in `ios/App/CapApp-SPM/Package.swift` to match the worktree's depth (`../../../../../../node_modules` instead of `../../../node_modules`). The file is tracked, so committing that breaks the iOS build for everyone in the main checkout. `Info.plist` is safe — sync leaves it byte-identical (only `cap add` rewrites it, via `editProjectSettingsIOS`) — but if you do run sync in a worktree, `git checkout -- ios/App/CapApp-SPM/Package.swift` afterwards.
- **Never let a Capacitor plugin pass through a promise.** A plugin object is a Proxy that answers *every* property name, `then` included. Resolve a promise with it — `import('@capacitor/geolocation').then((m) => m.Geolocation)`, or `return Geolocation` from an async function — and the promise machinery takes it for a thenable and calls the native method `then`, which does not exist: «"Geolocation.then()" is not implemented on ios» as an unhandled rejection, and a promise that never settles. That hung every position lookup in the iOS app from the #284 deploy on 17 Oct 2026 until the hotfix (#285) — «Identifiser» stood on «Henter posisjon …» — and it was the second time (`loadPlugin` in `src/lib/native/purchases.ts` documents the first). Cache the *module* and destructure the plugin after the `await` (a module object has no `then`), or wrap the plugin in a plain object, as those two files do. The tests passed because their fake plugin was a plain object: a fake plugin must be a Proxy that rejects every unknown method, `then` included (`src/lib/hooks/__tests__/useGeolocation-native.test.ts`).

## Conventions

- UI text in Norwegian; new strings should match tone of existing copy in `src/app/`. Don't translate user-facing copy to English.
- Zustand stores live in `src/store/`. TanStack Query for server-state caching is preferred over manual `useEffect` fetches.
- Tests live next to source in `__tests__/` folders. Pure utility functions (`src/lib/billing/plans.ts`, `src/lib/utils/prediction.ts`, `src/lib/utils/species-scoring.ts`, `src/lib/log/*`, `src/lib/rate-limit/*`, `src/lib/weather/*`) all have tests — keep that going. UI components are largely untested.
- The repository is **public**, so a recipe says *where* a secret is kept, never what it is. Three real ones — two account passwords and the company's IBAN — were pasted into `docs/` «just for now» and are still in the git history. `src/lib/__tests__/docs-uten-hemmeligheter.test.ts` is that rule as a test: no password, IBAN or «user / password» pair in `docs/`; no secret as a string constant in `docs`, `scripts`, `.claude`, `e2e`, `supabase` or `content` (read it from the environment); and no address at a private mail provider anywhere it reads, `src/` and `messages/` included — fixtures and examples use `example.com`.
- iOS zooms the whole page when a field under 16 px gets focus and does not zoom back out, so a global rule in `src/app/globals.css` (`@supports (-webkit-touch-callout: none)`) forces 16 px on inputs there. Do not fight it per component, and never «fix» the zoom with `maximum-scale=1` or `user-scalable=no` — that turns off pinch zoom for everyone. «Reduce Motion» is honoured by a global rule in the same file (Leaflet is exempt: it waits for `transitionend`); scrolling from code must ask `rulleAtferd()` (`src/lib/utils/bevegelse.ts`), because CSS cannot override an explicit `behavior: 'smooth'`.
- Commit message style: short imperative subject in English (matches `Step N: ...` history). Co-author the AI helper with `Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>`.
- The README and most planning docs are in Norwegian. `docs/strategi-2026-2027.md` is the current human-facing source of truth for priorities and what's left to build (`docs/roadmap.md` is history and says so itself); `docs/logging.md`, `docs/8-step-status.md`, `docs/commercial-mvp-plan.md`, and `docs/offline-map-mvp.md` are good orientation reads for understanding intended scope.
